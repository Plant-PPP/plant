# Decisions

Decisions that are not in the plan, or that detail it. Newest first.

## 2026-10-09 · MFA screens: verify at sign-in and turn TOTP on (PLA-76)

- **`/auth/mfa` asks an enrolled session below `aal2` for its TOTP code**, then reloads the page it was going to (`afterLoginPath(next)`) in full, so the proxy and the server read the `aal2` cookie instead of claims or a prefetch cached at `aal1`. It reads claims through `readSessionClaims()` (`lib/auth/session-claims-unchecked.ts`), the same check as `getSessionClaims()` without the redirect to `/auth/mfa`; lint lets only that page and `session-claims.ts` (and their tests) import it, and the two only call it. The proxy lets such a session through under `/auth/mfa`, so the page defines no server action (lint checks it) and imports none. A user with no TOTP factor, or whose factors cannot be loaded, sees why and can only sign out (`auth.mfa_page` logs it); one whose session has already ended, with a token still in date, is sent to sign in again.
- **"Cerrar sesión en todos tus dispositivos" is the way out of `/auth/mfa`** for a lost app or the wrong account. It revokes the other sessions first, then this device the way the user menu does (`lib/auth/sign-out.ts`). auth-js reports a revoke Auth refused for a dead session as a success, so after the revoke it asks Auth about this session: when this session had already ended (another device or a timeout), nothing was revoked, and it signs out here and sends the user to sign in again and retry. Any other failure, of the revoke or of that check, keeps this session and asks for a retry, since the revoke cannot be confirmed. Each other device keeps the access token it holds until it expires (up to an hour, `jwt_expiry`) and is signed out at its next refresh.
- **Ajustes (`/settings`) is new, reached from the user menu**, with one "Seguridad" card. Its switch turns TOTP on: the panel clears abandoned unverified factors, enrolls with issuer "Plant" and no friendly name (Auth rejects a repeated one), shows the QR and the setup key, and verifies the first code. That verify raises this session to `aal2` and Auth deletes the user's other sessions below it, which the success message says. In this PR the switch cannot turn TOTP off; that is the first sensitive action (PLA-76, third PR). A failed load of the factors disables the switch and offers a retry, never showing "off" to an enrolled user.
- **The browser alone enrolls, challenges and verifies**, because Auth rate-limits those per caller IP and from the server every user would share Vercel's. Lint lets only `lib/auth/mfa-browser.ts` (marked `client-only`) read `mfa` off an Auth client, and `mfa-factors.ts`, which the server imports too, only to list factors. Every web lint block now starts from the full list of module fences (`WEB_FENCES` in `apps/web/eslint.config.mjs`) and names what it may import, so an override cannot drop one by leaving it out.
- **One code field for both codes.** TOTP codes are always six digits, like the mail code (`otp-config.test.ts` pins them equal), so `/auth/mfa` and the panel use the login's `CodeInput`. The request state and its error copy are shared through `useAuthRequest`; MFA errors map to their own copy and fall back to the login's.
- **The QR is an `<img>` with a `data:` URL** (allowed by the CSP's `img-src`), on a white quiet zone so phone cameras read it in dark mode; Auth's SVG never reaches the DOM as HTML. Messages are inline (`role="alert"`/`role="status"`), as on the login, not toasts.

## 2026-10-09 · Audit rows for MFA and session end (PLA-76)

- **Four more `audit_log` actions, all from database triggers:** `auth.session.deleted`, `auth.mfa.verified` (a session raised to `aal2`), `auth.mfa.factor_verified` and `auth.mfa.factor_removed` (a verified factor deleted). Enroll, verify, unenroll and sign-out run between the browser and Auth, so only the database sees all of them. An unverified factor, a refresh and a failed TOTP attempt write nothing, and a TOTP verify on a session already at `aal2` (a step-up) writes only the `auth.session.deleted` rows of the sessions below `aal2` it deletes; Auth's logs keep the failed attempts.
- **One definer per table.** PLA-21's `record_session_created()` is renamed `record_session_event()` and handles insert, update and delete, deciding the action from `TG_OP` and the row's `aal` transition; its insert trigger is kept and a second trigger fires on delete or update. `record_mfa_factor_event()` serves `auth.mfa_factors`. Neither takes a trigger argument, so the floor's exact trigger definitions pin what each one writes. `auth.mfa.verified` means a session raised to exactly `aal2`; Auth writes no `aal3` today. Both read `id` and `user_id` as columns, so an Auth rename of either fails Auth's write instead of writing a row without an owner. The two inserts stay inline so each writer is parameterless and only a trigger can run it; a third definer on an Auth table extracts the shared insert into one `private` function with EXECUTE revoked from every role.
- **No column list and no `WHEN` on the triggers**, extending PLA-21's `to_jsonb` rule: a column named there would make an Auth migration that changes it fail on a dependency. The cost is a plpgsql call on every session and factor update (a refresh is two session updates, a challenge updates the factor) that compares one field and inserts nothing.
- **`auth.session.deleted` covers every deletion of a session row except a `TRUNCATE`**, which fires no row trigger: sign-out in any scope, the `aal1` sessions a TOTP verify deletes, user deletion and Auth's cleanup of expired sessions. A session that times out writes its row when the cleanup deletes it, not when it stops refreshing. It does not tell them apart; Auth's logs do, and account deletion (PLA-84) writes its own row. `metadata` holds `session_id` and `aal`, or `factor_id` and `factor_type`; never the factor's secret, its name or the session's key. `request_id` is always empty on trigger rows. A recovery-code factor is inserted already verified, so it would get a removal row and no verified row; recovery codes are off.
- **The migration needs only the `TRIGGER` privilege PLA-21 already used.** `auth.sessions` and `auth.mfa_factors` belong to Auth's role, so nothing here drops or replaces a trigger on them. The factor trigger is created before the session trigger, the order Auth locks the two tables in unenroll and a first verify; a request on another path that crosses the migration deadlocks, and either that request or the deploy is aborted once; the deploy is re-run.

## 2026-10-09 · MFA rules, part 2: the database gate and the app's checks (PLA-18)

- **Every `public` table has one RESTRICTIVE policy, "Requires two-factor authentication", for `authenticated` on every command**: the token is `aal2`, or its `mfa_enrolled` claim is `false`. A token without the claim counts as enrolled, so it reads and writes nothing below `aal2`. It overlaps part 1's `authenticated_aal1` role on purpose: the role covers what the hook demotes, the policy covers a token the hook never saw. A new table copies the policy verbatim (it is in `enforce-owner-isolation`'s house form): the pgTAP floor fails on a `public` table without exactly one RESTRICTIVE policy with that name, role, command and expression. Global reference tables keep it too: their floor exception covers the owner predicate and `user_id`, not the gate. The floor's gate assert checks only `public`: the first Storage bucket or private Realtime channel adds the same predicate as a RESTRICTIVE policy, and its assert to the floor, in its own PR.
- **One truth table, read three times.** The rows between `-- truth-table:start` and `-- truth-table:end` in `supabase/tests/mfa_gate_test.sql` drive the hook's asserts, the policy's (a read, an update and an insert per row, with the claims a real token carries) and, parsed by `apps/web/src/lib/auth/mfa-rules.test.ts`, the app's `mfaRequirement`. The parser rejects anything but the full grid with the shared claim key, and `turbo.json` lists the file as a global dependency so a changed row re-runs the web tests.
- **The proxy sends a session that needs the code to `/auth/mfa?next=…`** (`redirect_mfa`), and lets it through on `/auth/mfa` itself (`mfa_required`). `/login` and `/auth/callback` skip the check: the callback finishes a sign-in and its `next` lands on a page that is checked. A token without the claim gets the Auth-outage retry page and an error line (`mfa_claim_missing`, also its `error.type`), never a refresh per request, which would drain Auth's refresh limit. `x-plant-auth` carries the reason, and `getSessionClaims()` throws `AuthUnavailableError` with it, which `onRequestError` logs as the outcome. `getSessionClaims()` repeats the check where the proxy does not run it: routes outside its matcher, `/login` and the callback. The `/auth/mfa` screen is PLA-76's (it answered 404 until PLA-76's second PR, which no hosted user reached while every factor was off).
- **Export, account deletion and email change call `requireSensitiveSession(action)`** (`apps/web/src/lib/auth/sensitive-session.ts`), which answers `sign_in_again` unless the token's `amr` has a first-factor method (`FIRST_FACTOR_METHODS`: email code, mail link, Google, and `email/signup` for a brand-new user's first link) from the last 15 minutes, and logs each denial once (`auth.step_up`, `step_up_required`). A verified TOTP code does not count: a session thief can enroll their own factor, not prove the mailbox. The check runs in the server action, or where the job is enqueued, since a job event carries no user authority; in SQL only where the user's JWT reaches the function. It returns a `SensitiveSession` with only the user id, which the action takes as proof the check ran. `sign_in_again` needs `/login` to accept a signed-in user, which PLA-58, PLA-84 and PLA-76 build with their screens, together with the audit rows of denied actions (PLA-58, PLA-84) and of MFA changes (PLA-76: `aal` changes on `auth.sessions`, factor changes).
- **Email change:** Auth itself requires `aal2` from an enrolled user. For a user without a factor, the UI calls `requireSensitiveSession`; a direct call to Auth's API skips it, but Auth still mails both addresses and needs both confirmed.
- **Rollback**, in order. The hook stays on while the RESTRICTIVE policies or the app's check exist: without it every new token lacks the claim, the database refuses it and the app answers `mfa_claim_missing` to everyone.
  1. Until PLA-76, confirm every hosted MFA factor is still off, enrollment and verification. After PLA-76, step 4 opens every enrolled user's code-only sessions, so it waits for an explicit decision.
  2. In the dashboard's SQL editor, first note what is there (step 3 needs it): `select tablename from pg_policies where policyname = 'Requires two-factor authentication';`. Then `DROP POLICY IF EXISTS "Requires two-factor authentication" ON public.<table>;` for each table it lists.
  3. Merge an app-only revert of the MFA check: `mfaRequirement` and its uses in `apps/web/src/proxy.ts` and `lib/auth/session-claims.ts`, the reason in `lib/supabase/proxy.ts`, `lib/auth/session-state.ts` and `instrumentation.ts`, and their tests. `sensitiveRequirement`, `requireSensitiveSession` and `MFA_PATH` need no hook claim and stay once anything calls them. Keep `proxy.ts`'s `request.headers.delete(AUTH_UNAVAILABLE_HEADER)`: it is the only place a client's `x-plant-auth` is dropped. If step 2's query returned no rows, this migration never ran: approve no _Deploy migrations_ run until step 5 is merged. That run applies the policies and then their drops, each file in its own transaction, so a run that fails on the drops leaves the policies in place. Staging is a preview branch, so Vercel's instant rollback does not apply.
  4. Only then, and only if the hook is the fault, switch the hook off (part 1's rollback; its PR merges after step 5). If step 2's query returned no rows, the hook goes off only after step 5's _Deploy migrations_ run is green. Enrolled `aal1` sessions then reach data until it is back on; none exist while every factor is off.
  5. The rollback PR: a **new** migration with the same `IF EXISTS` drops, the floor's and `mfa_gate_test.sql`'s policy asserts reverted, the truth table out of `turbo.json` (step 3 removed its only reader in the web tests) and the gate out of every guide that names it (`git grep -n -i 'MFA gate' -- .agents .cursor`: the house form, its Storage note, `supabase-postgres-best-practices`, the migrations rule, the condensed owner lens and the PR-readiness manifest), green before merge. Migration files are never deleted: the append-only check refuses it, and `supabase db push` would find a remote version with no file.

## 2026-10-08 · AI costs (PLA-22)

- **One `ai_costs` row per model call**, written by `costMiddleware` (`apps/web/src/lib/ai/cost-middleware.ts`) around the model, priced by the model id the caller asked for, never the one the provider answers with. Each SDK retry and each tool step is its own call. Nothing else records costs: a second recorder in `onStepFinish` would count twice.
- **Ported from the reference app, with Plant's rules where they differ.** The model id is the type `PricedModelId`, so an unpriced model does not compile and there is no fallback price. Cache reads and writes have their own absolute prices, as Google publishes them, and `costUsd` computes exactly in BigInt and rounds the sum once, half up, to 10⁻⁸ USD, never in floats. `gemini-3.8-flash` carries its 2027 price, so its rows before 2027-01-01 read twice what Google bills: PLA-36 re-prices it if it ships first, or the quotas (PLA-42) allow for it. `model_id` is `text`, not an enum: it is the provider's API id, `PricedModelId` already closes the set in code, and adding a model stays a change to `pricing.ts` alone. No reference columns yet: `imports` (PLA-34) and the chat (PLA-50) add a nullable FK each. No Bedrock, deployment column or prompt-cache helper: Plant calls providers directly, and caching arrives with the chat (PLA-47). No tracked-model factory or provider map until PLA-36 designs how `packages/jobs` gets one per run.
- **`service_role` writes, with a column-level `INSERT` and nothing else**: Inngest steps have no user session, and a minted per-user JWT is more infra than one grant. `ai_costs` departs from the owned-table shape on purpose: no `DEFAULT auth.uid()`, no write grant to `authenticated`. The owner can `SELECT` their own rows, which the pgTAP floor requires of every `public` table; the UI never shows dollars, and a user calling the API sees only what their own calls cost.
- **Who is billed comes from the session or a row the server loaded** (`getSessionClaims().sub`, an import's `user_id`), never from a request body, an event payload or model output, because the writer bypasses RLS (`AiCostContext`'s doc comment). Nothing checks it yet: PLA-36 and PLA-47 brand the id with their first caller.
- **The secret key has one importer.** `SUPABASE_SERVICE_ROLE_KEY` is also the Auth admin API (sign in as anyone, delete users) and a Storage policy bypass, so only `lib/supabase/service-role.ts` (and its test) reads it, only `lib/ai/ai-cost-sink.ts` (and the client's test) imports that module, and only route handlers under `src/app/api` and the sink's own test import the sink, which may never be or hold a `"use server"` action; neither module may be handed on through `export … from`, an export list or a default export, and `src/lib/ai` may not re-export `ai` or a provider package. ESLint enforces it over every file in `apps/web` (configs and e2e included), on every source extension, with or without the extension in the specifier, for `import()` and direct `require()` calls too (a `require` wrapped in a type cast is banned), and bans computed specifiers, `require.context` and paths into `node_modules`, which the fences cannot read. Everywhere, in packages too, it bans Inngest's `step.ai` (any `ai` property or destructured key, bare, quoted, as a template literal or in a type cast), `@inngest/ai` and `@inngest/agent-kit`, which call a model past the cost middleware, until a caller routes them through it. It flags the key by name (also as `NEXT_PUBLIC_`), in `packages/*` and `security-tests` too, which may not import from `apps/`, the AI SDK, or the service-role client or the sink by file name either (`eslint.fences.mjs`, `eslint.packages.mjs`); a name built at runtime, `require` reached through another binding, an inline `eslint-disable`, or a re-export through a file no package lints (the repo root, `scripts/`, `evals/`) gets past it, which review catches. It also keeps `ai` and the provider packages inside `src/lib/ai` (`@ai-sdk/react` stays open). `scripts/web-import-fences.test.mjs` (`pnpm test:scripts`) lints each case it must catch or allow. `check:boundaries` lets only `apps/web` and `evals` declare `ai` or `@ai-sdk/*`, and only `apps/web` Inngest's model packages, reads the package an alias or path spec installs, and fails on any other spec than a version range, tag, `catalog:`, alias or path to a workspace package (a tarball, URL, git spec, or a path outside the workspace, which installs its own dependencies unchecked); evals spend dev keys with no user, outside `ai_costs`. Without the key the sink rejects with `missing_key` and the call still succeeds. Vercel gets the key with its first deployed caller (PLA-36).
- **The writer waits 1.5 s and throws a sanitized error**: `timeout`, `fetch_error`, `missing_key`, the SQLSTATE or PostgREST code, or `http_<status>`, never Postgres's `details` or `hint`, which carry the row. Only a 201 counts as written: postgrest-js reports a few other answers as success. A timeout, a fetch failure or any 5xx may still have committed, so it logs `plant.ai_cost.reason` `unknown`; anything else wrote nothing, `not_written`. The code is also the line's `error.type`. The amount travels as a decimal string (the generated types say `number` for `numeric`).
- **Recording never fails the call; every billing gap it can see is logged.** `ai_cost.record_failed` (error) when the row was not written, `ai_cost.unbilled` (warning) when the provider may have billed with no row (`aborted`, `call_error`, `no_finish`, `stream_error`, and `usage_missing` when the provider sent no token count, which writes no row rather than a zero one), and `usage_partial` next to a row whose stream sent an error part before it finished, since a chunk the provider could not parse may have held tokens the row lacks. A provider's error status (`APICallError` with 4xx or 5xx) logs nothing unless the call was aborted: the provider did not bill, and the SDK retries or the caller logs the failure. Any other failure logs `call_error`, the AI Gateway's included, because it makes up statuses for its own timeouts and lost connections. A function frozen or recycled while its row is in flight logs nothing at all, and neither does an `@ai-sdk/anthropic` stream whose first event fails to parse, which that package reports as a 500. The lines carry `enduser.id`, `plant.cost_type` and `gen_ai.request.model`, plus the provider's `http.response.status_code` on a `call_error`, `aborted` or `stream_error` line whose error it answered, never the row, tokens or amount; `serverLog` masks keys that name amounts, prices, balances or credentials anyway.
- **`prompt-text.ts` neutralizes untrusted text** before a prompt: every line terminator becomes a space and `<` and `>` are dropped, so a document cannot start an instruction line or close a tag block such as `</document>`; prompts delimit untrusted text with tags, since a fence of backticks, quotes or dashes is not neutralized. Line terminators are Unicode's (UAX #13) plus the separators U+001C–U+001E; the brackets include their small, fullwidth and not-less/not-greater look-alikes, the combining slash (U+0338) that NFC would join with a template's own bracket, and the invisible tag characters, and lone surrogates go too, since removing a bracket between two halves would make a tag character.
- **A streamed step finishes only after its cost is recorded.** A consumer that stops reading does not stop the model stream, so the row is still written; an abort does. The chat (PLA-47) must not pass the browser's abort signal to the model and must `consumeStream()` and keep the request alive with `after()`, or a closed tab leaves calls unbilled. Recording takes up to 1.5 s inside the step, so a caller's `totalMs`, `stepMs` or `chunkMs` timeout must leave room for it, or the timeout aborts the step while its row is being written (the row is still written) (PLA-36, PLA-47).

## 2026-10-08 · MFA rules, part 1: the access token hook (PLA-18)

- **TOTP is optional, and once a user has a verified factor every session of theirs needs `aal2`.** Nobody has to enroll to use Plant. A user who did enroll is asked for the code at sign-in, and the database refuses their `aal1` tokens: otherwise a stolen code-only session of an enrolled user would keep full access. Export, account deletion and email change additionally need a sign-in with the mailbox (code or link) or Google in the last 15 minutes (part 2), not "enroll TOTP first": whoever holds a stolen session can enroll their own factor (Auth asks for `aal2` to enroll only once a verified factor exists), but cannot prove the mailbox.
- **Two PRs, because the database gate must not land before the hook runs on the hosted project** (`plant-staging` is also production's database until the beta). Part 1 adds the hook and a role; Tomas turns the hook on in the dashboard; part 2 (the RESTRICTIVE policies and the app's checks) waits until every token in use carries the claim, one JWT expiry later.
- **`private.custom_access_token_hook` adds `mfa_enrolled` to every access token** (a JSON boolean: any verified factor, of any type) **and gives an enrolled user's token below `aal2` the role `authenticated_aal1`**, which holds no grant: PostgREST answers 42501 on every table, view and function, and with USAGE on no schema but `public` it is refused by Storage, GraphQL, Realtime's private channels and any future RPC outside `public`. It overlaps part 2's policy on `public` tables, and keeps covering whatever Plant later exposes to `authenticated` outside `public`, which that policy does not reach. The hook lives in `private`, runs as Auth's `supabase_auth_admin` (`SECURITY INVOKER`, empty `search_path`), which alone can execute it besides its owner, and reads the user from Auth's event, never from the request. Its rule is the truth table in `supabase/tests/mfa_gate_test.sql`, which part 2's policy and the app's TS rule will read too.
- **A hook error fails the sign-in or refresh** (it runs in Auth's transaction with a 2 s timeout). A refresh then shows as the proxy's `auth_unavailable` with `error.type: "timeout"`, like any Auth outage, because auth-js retries Auth's 5xx past the proxy's 5 s limit; an email-code sign-in fails in the browser and Plant logs nothing. Only Auth's logs show it was the hook; alerting on them is PLA-73's.
- **The claim key and the first-factor `amr` methods live in `@plant/shared`** (`MFA_ENROLLED_CLAIM`, `FIRST_FACTOR_METHODS`), so part 2's app rules and the pentest read one list. `otp` in `amr` means any `POST /verify`, so the list proves the mailbox only while phone sign-in, SMS codes, other providers, passkeys, SAML, linking, third-party and Web3 tokens stay off: `otp-config.test.ts` pins that in `config.toml`, and `auth.pentest.test.ts` checks the providers, passkeys and SAML against the running Auth. The hosted project keeps its own copy of every Auth setting in the dashboard, which is the source of truth there; the PR checklist covers it.
- **auth-js's `mfa.getAuthenticatorAssuranceLevel()` is not used**: without a JWT it trusts the session's unverified `user.factors`, and with one it calls Auth's `/user` on every request.
- **Auth checks the session's `aal`, not the token's role**, for enrolling another factor, removing a verified one and changing the email: a demoted token still reaches `GET /user`, `PUT /user` with `data` (`user_metadata`, never trusted), reauthentication (which mails the owner a code), sign-out, including the global one that ends the owner's other sessions, and the challenge and verify that climb back to `aal2`.
- **Every hosted MFA factor stays off, enrollment and verification alike, until the MFA screens (PLA-76)**, and so does the "MFA factor enrolled" mail until Resend (PLA-75): a factor created before the hook is on could otherwise be verified later and lock its owner out. PLA-76 ships after part 2, because without part 2's redirect to `/auth/mfa` an enrolled user's code-only session meets 42501 everywhere and is never asked for the code; TOTP is set to Enabled once its three PRs are on staging, and Phone stays Disabled. Locally TOTP is on, for the pentest.
- **Rollback:** the hook goes off only after part 2's rollback steps 1 to 3, and the PR below merges only after part 2's step 5. The hook goes off in the dashboard first, by switching off "Enable Customize Access Token (JWT) Claims hook" and clicking Update hook (Delete also grants EXECUTE on the function to `anon`, `authenticated` and `PUBLIC`), and a token from a new sign-in on staging must no longer carry `mfa_enrolled` (the PR's checklist has a console snippet that decodes it). Then a PR with a new migration drops the function and revokes `supabase_auth_admin`'s USAGE on `private` (the floor then asserts that USAGE is gone), restores the commented-out hook and TOTP off in `config.toml`, and removes `mfa_gate_test.sql`, `mfa.pentest.test.ts`, `totp.ts`, the MFA vocabulary and everything else that names them or the hook (`git grep -e custom_access_token_hook -e mfa_enrolled -e MFA_ENROLLED_CLAIM -e FIRST_FACTOR_METHODS`), keeping the floor's `authenticated_aal1` asserts, and `FIRST_FACTOR_METHODS` with `sensitiveRequirement` while anything calls `requireSensitiveSession`; developers restart their local Supabase after pulling it, or their Auth keeps calling the dropped function. From then on the hook stays switched off in the dashboard: switched on, it would fail every sign-in. One JWT expiry later, another migration runs `REVOKE authenticated_aal1 FROM authenticator` and `DROP ROLE`, and removes what still names `authenticated_aal1`. Migration files are never deleted.

## 2026-10-08 · Logs and audit (PLA-21)

- **Every new Auth session writes one `auth.session.created` row to `audit_log`**, from an `AFTER INSERT` trigger on `auth.sessions`. Auth creates the session: the email code is verified from the browser, and `/auth/callback` exchanges Google's and the mail link's code but sees only Auth's answer. The trigger sees every sign-in whatever the method, and also recovery, email change and identity linking, which create sessions too. A method-aware `auth.login` can be added later without narrowing it. A refresh updates the row and writes nothing.
- **Sign-in is fail-closed.** The trigger's insert runs in Auth's transaction: if it fails, the sign-in fails, so a failing insert cannot leave a session unaudited. A trigger that does not fire (replica mode, or dropped by Auth's own role) fails open; the threat model records it. Any later change to `audit_log` is on the sign-in path, and since PLA-76 also on sign-out, TOTP verify, unenroll, user deletion and Auth's cleanup of expired sessions; `audit_session_created_test.sql`, `audit_mfa_test.sql` and the pentest sign-ins in the CI `database` job pin that the insert stays valid. The trigger reads only `auth.sessions.id` and `user_id` directly; `aal` goes through `to_jsonb`, so an Auth upgrade that drops it cannot break sign-in.
- **`SECURITY DEFINER`, `search_path = ''`, owned by the owner of `audit_log`.** Auth's role holds nothing on `audit_log`. No API role can insert into `auth.sessions` directly. The `service_role` key can still create a real session for any user through Auth's admin API, and its row looks like a sign-in. The pgTAP floor pins each definer to the table it fires on.
- **`audit_log.action` and `outcome` are enums** (`private.audit_action`, `private.audit_outcome`), extend-only: a new value is `ALTER TYPE … ADD VALUE`, never a rename. `outcome` is `NOT NULL` with no default, so every writer states it; `failure` and `denied` are there for the upload rows to come. Changing `action`'s type and dropping its `CHECK` is the one exception to additive-only migrations: nothing had written to the table or read it. It drops no data, so the PR is not marked `[DESTRUCTIVE]`.
- **`metadata` holds `session_id` and `aal`**, or `factor_id` and `factor_type` since PLA-76. Its size cap arrives with the first writer that takes outside input. Retention waits for the lawyer review (PLA-56).
- **`serverLog.audit` and a `service_role` writer move to the first server-side action that needs auditing**, the upload in "Carga con IA". Until then the triggers are the only writers, which also supersedes the PLA-16 migration's note that a server writer, its grants and its policies arrive with PLA-21.
- **Server code logs through `serverLog`** (`apps/web/src/lib/log/server-log.ts`) and `no-console` is on in `apps/web` and every package. One JSON line per call, flat fields, the event name a static, dot-namespaced name, `level` matching the outcome (error only for a final failure). The logger writes `level`, `event`, `trace_id` and `span_id` last, so a field cannot replace them; Vercel stamps the time. On a line with an error, `error.type` is its code when it has one (Auth's, Node's), else its class, so one failure reads the same everywhere; `exception.type` is the class.
- **Every string is scrubbed, then cut** (`credential-scrub.ts`): Auth's code and token params raw or percent-encoded once or twice, tokens, keys, secrets and passwords in JSON, JSON escaped once or `name: value` form, the PKCE code and verifier, JWTs whole or cut, bearer and basic values, Supabase's auth cookie and secret keys, Inngest's signing keys, emails accented or encoded, and CBU, CUIT and DNI bounded by digits, so one glued to a word in a file name, or after a percent escape in an encoded one, is masked. UUIDs, hex ids of 16 or more characters (except 11 or more digits with only letters around them, a CBU or CUIT glued to a word) and times are kept, since their digit groups would read as a DNI; any other 7 or 8 digits, a byte count or a date in a file name, are masked. A field whose key names money, holdings, an identity number, a contact or a credential is masked whatever it holds, except counts, durations, ids of money and holdings and `gen_ai.*` token counts. A value is read up to 4096 characters, scrubbed and cut to 512; an exception's stack up to 8192 characters and 4096.
- **One `proxy.request` line per proxied request**, prefetch and RSC requests included: `plant.request_id`, method, `url.path` without the query, `plant.outcome`, Auth's duration, `enduser.id` from the verified claims, and `error.type` only when the session could not be checked: Auth's code (or the error's class) when Auth is unavailable, `no_auth_config` without Supabase. Otherwise Auth's code is `plant.auth.reason`: a missing session is not an error. `error.type` marks every failure line; an Auth outage also fails the page's own check, so a failure rate counts distinct `plant.request_id`s. No status code: a pass-through is 200 even when the page fails, and Vercel's request log has the real one. The proxy logs its own crash, because Next 16.4 does not run `onRequestError` for the proxy, which is always Node; `onRequestError` skips the proxy in case that changes.
- **`onRequestError` logs uncaught errors** in pages, route handlers and server actions as `request.error`. It and `/auth/callback` keep a request id read from the header only if it is a UUID, so the field never carries arbitrary text; outside the proxy's matcher the id is the client's, so it can still name another request. `AuthUnavailableError` (the page's half of an Auth outage) is a warning without a stack, and so is Next's error for a malformed router state header (`plant.outcome` `bad_request`), which any client can send.
- **`/auth/callback` logs one `auth.callback` line** with a static outcome (a throw is `onRequestError`'s `request.error`); never the code, `error_description` or Auth's message. A missing code or a failed exchange is a failed sign-in and carries `error.type`, even when the cause is a link opened in another browser; a refusal on Google's screen is the user's choice and an expired or used mail link is the user's old link, so both carry `plant.auth.reason`. Any other OAuth error carries `error.type` `_OTHER` and Auth's `error_code` as `plant.auth.error_code` (`_OTHER` when it is not snake_case). Anyone can request the callback with any `error` and a snake_case `error_code`, so its warnings are unauthenticated input and must not page anyone. A failed exchange is a warning too, with the error's status as `plant.auth.status` (Auth's HTTP status when Auth answered; auth-js sets 400 for a missing verifier and 500 for an answer without a session): Auth answers a code Postgres cannot store (a NUL) with a 500 as well, and anyone can send one, so 5xx lines alone do not prove Auth is failing; `auth.callback` `signed_in` lines dropping to zero do.
- **OpenTelemetry is off without an endpoint.** `register()` loads `@vercel/otel` only when `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set, traces only, and never rejects (Next would fail every request after it). Each line carries its span's `trace_id`, not `x-request-id` as a span attribute: `@vercel/otel` reads the headers before the proxy replaces a client's copy. The proxy and the page run as separate traces; `plant.request_id` joins their lines.
- **Before PLA-73 sets an endpoint, a span processor must scrub `http.target`, `http.url` and fetch span names.** Next puts the query there, and `/auth/callback`'s carries the PKCE `code`; Vercel's own request log already shows it. A Vercel tracing integration (`VERCEL_OTEL_ENDPOINTS`) makes `@vercel/otel` ignore the OTLP variables. Default fetch spans carry outbound URLs in their attributes and names; so Supabase REST filters must stay ids, never amounts, until that processor exists. Next adopts a client's `traceparent`, so a client can choose a line's `trace_id`.

## 2026-10-08 · CSP and security headers (PLA-19)

- **`proxy.ts` sends the CSP, with a fresh nonce on every request.** Next reads the nonce from the request's CSP and stamps it on its own scripts; the root layout passes it to `ThemeProvider` for next-themes' inline script. Reading the request makes every page dynamic, which a nonce needs: a static page is built with no nonce, so the CSP would block its scripts.
- **`script-src 'self' 'nonce-…'`, no `'strict-dynamic'`.** Every script Plant loads is its own; `'strict-dynamic'` would let any nonced script load others from anywhere. `'unsafe-eval'` only under `next dev`, which needs it. The e2e fails if production allows eval.
- **`style-src 'unsafe-inline'`.** The sidebar renders `style` attributes with its CSS variables, which a nonce cannot cover. Styles cannot run code.
- **`connect-src` adds Supabase** (HTTP and WebSocket), because the browser calls Auth directly (PLA-17).
- **One CSP.** `next.config.ts` holds the headers that are the same on every route (HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`); the CSP, with `frame-ancestors 'none'`, comes only from the proxy. ## 2026-10-07 · Migration gates and deploy to `plant-staging` (PLA-11)

- **The reference app's behavior, not its file layout.** Same checks, same `.squawk.toml`, same self-test and the same push-only `db push`, with three differences: (a) the checks on new migrations live in `scripts/check-migrations.sh`, called from the `database` job, because a workflow with `paths:` cannot be a required check; (b) squawk is pinned in `package.json` like the Supabase CLI (PLA-7), with no separate version files; (c) `deploy-migrations` lives in `ci.yml` with `needs: [database]`, because `needs:` only works within one workflow, and the reference's deploy runs in parallel with CI and can apply a migration CI rejects.

Accepted for now: exploiting it needs a network position between the GitHub runner and Supabase. `sslmode=verify-full` with Supabase's CA is the fix if that changes.
- **`forbidden-words` comes only from `forbidden-words.yml`,** which runs on pushes to this repo. A PR from a fork, or whose head was pushed with `[skip ci]`, never gets that required check and needs a ruleset bypass.
- **Shared database until the beta.** `plant-staging` is also production's database, so migrations are additive only: a `DROP` or `RENAME` waits until production runs code that no longer uses it.
- **Procedures:**
  1. A merged migration that never applied (it failed on the real database or landed out of order). If it failed on `lock_timeout`, first "Re-run jobs". Otherwise a PR moves it with `git mv` to a new timestamp and fixes it there; it is never edited in place, because the push only checks added files. The append-only check stops that PR, so Tomas adds himself as a ruleset bypass actor in "For pull requests only" mode, merges only that PR and removes himself right away. The push checks the new file's name, order and squawk, and the deploy applies it. A failed `CREATE INDEX CONCURRENTLY` leaves an INVALID index behind: the fix PR first adds a migration with only `DROP INDEX CONCURRENTLY IF EXISTS <name>` and the exemption line of `pass-concurrent-index-alone.sql`, then the build under a new timestamp.
  2. With `deploy-migrations` or `database` red on `staging`, the next merge is the fix and nothing else: the next push only checks its own changes. A migration left unapplied goes out with the next push, whatever it changes.
  3. The concurrency group keeps one pending deploy, including one waiting for approval, and the last one queued replaces it, so with merges close together an older SHA can replace a newer one. Nothing is lost: any later push deploys whatever is still unapplied, or "Re-run jobs" on the newest cancelled deploy.
  4. A merge with `[skip ci]` does not deploy until the next push.

## 2026-10-07 · Profiles, consents and audit log (PLA-16)

- **`REVOKE ALL` before every grant.** With `auto_expose_new_tables = false`, a new table in `public` still gives TRUNCATE, REFERENCES, TRIGGER and MAINTAIN to `anon`, `authenticated` and `service_role` by default. Every table runs `REVOKE ALL` from the API roles and removes those four from `service_role`, which with auto-expose off gets nothing else: it ends up with no privileges, and the first server code that uses it brings its own `GRANT`. `schema_rls_and_grants_test.sql` fails if `anon` has any privilege on a table in `public` or `private`, or if anyone other than the owner has one of those four.
- **Extensions:** `CREATE EXTENSION … WITH SCHEMA extensions`, always. In `public` every function of the extension would be exposed as an RPC; the floor checks it.
- **Shape of owned tables**: `user_id uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users (id) ON DELETE CASCADE` (the default is what allows inserting without a grant on `user_id`), primary key `uuid DEFAULT gen_random_uuid()` (a sequence id reveals how much others write), every `*_id` reference to another owned table as a composite FK with `user_id` (to a partitioned table, also with its partition key; if the reference is optional, `ON DELETE SET NULL (<column>)` so `user_id` is not nulled) and unique keys that include `user_id` or only columns the server generates (such as `id`). A one-row-per-user table (such as `profiles`) uses `user_id` as its primary key and has no `id`. A uuid that references nothing does not end in `_id` (for example `idempotency_key`), and a list of references goes in a join table, not in a `uuid[]`. `authenticated` writes only through column-level grants, never on `id`, `user_id` or columns the server maintains. A Storage path the user writes carries `CHECK (starts_with(<column>, user_id::text || '/'))`; the floor adds that check with the first table that has one. A partitioned table has primary key `(user_id, <partition key>, id)`, and every partition gets `ENABLE ROW LEVEL SECURITY` and the same `REVOKE ALL` with no grants: it is read and written through the parent. Our own helper functions (not `auth.uid()`) do not go in a `CHECK`, a default, a policy, an expression index or a generated column: they run as the user and would need EXECUTE. Use the expression or a `DOMAIN`, or a column the server maintains with a trigger (for example, the name without accents for search) and a plain index on it. The pgTAP floor checks `user_id` NOT NULL and cascading from `auth.users`, ids without sequences, unique keys with `user_id` or server-generated, that every uuid `*_id` column is its single-column primary key or an FK (paired with `user_id` when it points to another owned table), that there are no `uuid[]` columns, and write grants only per column and never on `user_id`; each table's two-user test covers the rest.
- **Global reference tables** (quotes, instruments) arrive with their feature and add a narrow exception to the floor: no `user_id`, only SELECT for `authenticated` and a `FOR SELECT USING (true)` policy.
- **Closed values as Postgres enums** (`reference_dollar`, `consent_kind`), so the generated types bring the unions and the TypeScript does not copy the literals.
- **Account holders are not in `profiles` yet.** They arrive with the feature that uses them (accounts and holdings), like every other table.
- **`consents` is a history.** Withdrawing a consent is a new row with `granted = false`; the current state is the latest row per kind. `granted` has no default, so every row says explicitly whether it grants or withdraws.
- **`audit_log` lives in `private` and has no FK to `auth.users`**, so the trail survives account deletion. It has no policies or grants. PLA-21 decided, on the still-empty table, `outcome` and the action vocabulary (enums) and the shape of `metadata`; the cap and retention come later. `metadata` never carries emails, IPs, amounts or document text.
- **plpgsql_check runs inside pgTAP**, because `supabase db lint` skips trigger functions, which today are all of them.
- **The CI `database` job uses the CLI pinned in `package.json`** (`pnpm exec supabase`) and does not log in to ghcr.io, so the workflow stays at `contents: read`. If the image registry starts rate-limiting pulls, the login gets added.
