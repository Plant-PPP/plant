# Decisions

Decisions that are not in the plan, or that detail it. Newest first.

## 2026-10-14 · Findings from a full-repository review

- **Imported cash is a cash holding.** A provider's draft row can be cash (`assetClass: "cash"`, `import_items.asset_class`), one per currency: balances of several accounts in a currency (IOL's, IBKR's) are added up. The review names it as Activos does ("Efectivo USD") with its amount and no price or portfolio. `confirm_import` takes it as the account's whole cash in that currency, checked against the cash holdings the review read, which it sends back with the rows, so cash edited in between is refused as stale:
  - with no cash holding it opens one in the account's default portfolio;
  - with one it sets its amount;
  - with several it refuses the row, and the review says to update them by hand.

  Cash is written as of confirmation, with no history. Wallbit's USDC and USDT stay their own crypto rows.

- **Balances Plant does not keep are counted.** For every exchange using `balanceRow`, and for IBKR, IOL and Nexo, a fiat Plant does not keep or a negative balance counts as a skipped row. One list of those fiat currencies (`OTHER_FIAT`: every ISO 4217 fiat but ARS, USD and MNT, which exchanges list as Mantle) serves the exchanges; Wallbit's checking account keeps only ARS, USD, USDC and USDT and counts any other non-zero currency, one it does not list too, as skipped. Wallbit's investment account's tickers that match a currency's code (COP, PEN) are stocks, and its `USD` is its dollars, added to checking's. Wallbit's trades still skip the code of any currency its API lists, as a trade does not say whether it is an exchange. A figure a provider sends as a string with more than eight decimals is rounded, as a number is. Mercado Pago counts a skipped row only when the closing balance does not read. A sheet row whose currency comes from the model's default is medium confidence. A currency cell Plant does not recognise skips the row, and an average cost that also reads as thousands is flagged too.
- **Provider bodies are capped**: 2 MB of JSON, 20 MB for an IBKR statement and 5 MB for a Mercado Pago report. Past the cap the read fails for good.
- **No cause crosses a job step.** Steps rethrow failures without their cause, and `SourceError` is never built with one, so the model's raw answer or a request's URL never reaches the run history. A store failure past retries logs at error level with `plant.import.store_step` and `plant.import.store_code`, carried in the error's message because Inngest drops custom error fields.
- **The export asks for a recent sign-in, is limited and is audited.** `exportData` hands its read to `auditedExport`, the one export of `export-audit-sink.ts` and the only thing the settings actions may import from it (the lint fences hold both), so no server action passes an audit outcome. It allows 5 exports per user a minute, in memory per serverless instance; past them it answers limited, which the card says, with no audit row. It refuses a stale session (signing out, then `/login?next=/settings`, like turning TOTP off) and writes `data.exported`: it takes the user from the session's verified claims and calls `public.audit_data_export`, a SECURITY DEFINER function only `service_role` executes, so a session cannot write its own rows with any outcome. `public.record_data_export` is no longer executable by anyone and goes in a later migration. Its outcomes are `denied`, `failure` and `success`. The tables are handed over only once the success row is written. Imports export up to `MAX_ROWS - 1`, and any table cut marks the file partial, which the card says.
- **Ledger reads**: the holdings' revisions are read before the movements, and movements are paged by keyset on `(date, rank, id)`, each page bounded by `date >=` the last row's for the index, so a write during the read leaves a stale revision that `write_operation` refuses. Holdings are still paged by offset; past 1000 instrument holdings a repeat only shows twice.
- **Span scrubbing** runs `scrubSensitiveText` and the Flex token mask over every span name and URL attribute (`http.url`, `url.full`, `http.target`, `url.query`, `next.span_name`), wherever the URL sits in the text.
- **An instrument holding's units are written only inside `write_operation`**: inserting one, or updating its amount, raises 42501 for `authenticated` without the transaction mark PLA-147 uses for movements.
- **Pinned charts are capped at 12 by a trigger** (hint `pinned_charts_full`), the same number as `MAX_PINS` (`max-pins.test.ts` reads it from the migration). Re-pinning a chart already pinned skips the count, so the unique key answers 23505 ("already") even at 12.
- **A price alert reads the latest quote in its own currency**, filtered before the latest is picked.
- **Connecting an API key is rate limited**: at most 5 provider checks per user a minute, in memory per serverless instance, so Plant is no oracle for someone else's credentials. Reading an institution's icon allows 10 per user a minute. Neither has a budget per instance, so users who spend theirs lock out nobody else (`userLimiter`).
- **A manual price is stated in its instrument's catalog currency**; another currency is refused as invalid. Core's `admitManualPrice` holds the rule for the app and the prototype, and a trigger on `manual_prices` refuses it (22023) for a write straight through the API. Rows written before the trigger stay as they are.
- **An import that stops being read before its draft is saved** (its account deleted meanwhile) is logged as skipped with `plant.import.skip_reason: "gone"`.
- **A failed alerts read in Ajustes or Resumen** shows a notice (in Ajustes' card, in Resumen's met alerts) instead of an empty list.
- **The review words what a reading left out by what it read**: a sync's balances or holdings it could not bring, a document's holdings left out, a spreadsheet's rows it could not read (`ImportItem.origin`, from the uploaded file's type).
- **A provider's refusal of an AI call** is logged as `ai.call_failed` with its error type and HTTP status, never its message, and the import it was reading (`plant.import.id`).
- **An import confirmed against cash or holdings that changed since the review read them** (`confirm_import`'s `stale`) answers `stale`, logged as a warning, and the review asks to check and confirm again.
- **An IOL price a decimal string cannot hold** (more than 8 decimals or 12 integer digits) is refused as that row's price, never failing the feed's run.
- **A sync that reads a currency at zero leaves the account's cash in it as it was**: draft rows need a positive quantity, so bringing cash to zero by import waits for a change across the draft, the review and `confirm_import`.
- **Quote feeds declare whether they are listed** (`RawQuoteFeed.listed`). A listed feed's Friday price is the market's last on the weekend; shared code names no source.
- **Indexes** on `uploaded_documents (delete_after) WHERE file_deleted_at IS NULL` for the file deletion job and on `uploaded_documents (storage_path)` for the orphan sweep.
- **A spreadsheet past its row limit says so.** `readSheet` reads `SHEET_ROW_LIMIT` rows from the top of the sheet's used range (blank rows count) and as many more to look ahead, and marks the sheet `truncated` when a non-blank row comes past the limit, or when the sheet goes on past what it read with no lookahead left to tell; blank lines or styled empty cells under a table do not mark it; `sheetToDraft` then counts at least one skipped row, since it cannot count the unread ones, and the review shows its notice.
- **Operations and debts carry their skipped rows** to `imports.skipped_rows`, and their reviews say how many were left out, as the holdings review does.
- **An import deleted after the job prepared it** (no row for its institution) is skipped as `gone` before any model call, never retried as a store failure. An import whose row is still there but whose file is not fails as `unreadable`, so it never stays "reading". The store refuses to download a path outside `<userId>/imports/`.
- **A queued sync is started again only for the same request** (draft and days); another request while one is queued answers `in_progress`.
- **Rows that two readings make past the draft's limit together** (holdings, operations or debts) count as skipped rows.
- **Uploading again a file whose import is still queued** starts its job as a retry, under a new event id, as a sync does.
- **A sync's holdings review never speaks of a document.** It shows no totals panel (a connector prints no total), its holdings not listed read "No vinieron en la sincronización", and a balance with no page reads "De la sincronización".
- **A debt balance typed that is not a number** asks for a valid number, as the minimum payment does.
- **`write_operation` clears its transaction mark before it returns.** The mark is local to the transaction, so left on it let whatever followed `write_operation` or `confirm_import` in the same transaction write operations, movements and instrument units by hand, and pg_graphql runs a whole request as one transaction. The mark now covers only `write_operation`'s own run. Plant reads and writes only through PostgREST, so GraphQL could also be turned off (`graphql_public` out of `api.schemas` in `supabase/config.toml` and the dashboard); that is left to a separate change.
- **A sync period's days fall between 2000-01-01 and 9999-12-31**, and only a sync of operations carries one (`imports_sync_period`). `syncAccount`'s period schema holds the same bounds; its ISO dates have four-digit years.
- **One capped body reader**: `readCappedBytes` in `@plant/shared` reads a response up to a cap, failing or cutting past it, and ignores a failed cancel. The quote feeds and the institution icons use it; `bodyText` in `packages/sources/src/connections/http.ts` should adopt it next.

## 2026-10-14 · Connectors: Roxom, Mercado Pago, Bitso and Ripio Trade (PLA-162)

- **Four more adapters on the same port, holdings only.** Each is its adapter, its line in `connectionAdapters()` and its `PROVIDERS` copy; none needs a migration (the provider check is a pattern since PLA-155). The only change outside them: the web app bounds each credential value at 4096 characters instead of 512, so a PEM private key fits, and checks the whole object against the database's 4 KiB cap (measured as Postgres prints the jsonb), so an oversize one is `invalid`, not a failed write. Shared helpers moved into `connections/http.ts`: `hmacSha256` (Binance and Nexo use it too) and `balanceRow`/`balancesReading`, which turn an exchange's balances into holdings: pesos and dollars as cash, other fiat (`OTHER_FIAT`: MXN, BRL, COP, CLP, PEN, UYU, EUR and others) left out, any other currency as a crypto asset in units valued in dollars.
- **Roxom**: an API key id and the user's RSA private key (PKCS#8 PEM, as Roxom hands it out), each request signed with RSASSA-PKCS1-v1_5 over SHA-256 of `GET:<path with query>`, in base64. The PEM is checked for shape by the schema and for being a key by importing it, before any request; a form's input drops its line breaks, so whitespace inside it is taken. Holdings are `GET /v1/accounts/balance?unit=btc`, each asset's `current`. **Positions and the transaction log are not read**: `/v1/positions` needs a symbol per call and its rows are leveraged perpetuals margined in BTC (the margin is already in the balance), which a holding of units does not represent; the log's fills, deposits, withdrawals and funding fees have no operation kind in the review. Roxom keys cannot be limited to reading (`readOnly: "none"`): the user confirms.
- **Mercado Pago**: the user's production access token, which has every permission (`readOnly: "none"`, confirmed). The review has no cash movements (operations are purchases, sales, dividends and coupons), and the settlement report has no balance column, so **Plant reads the released-money report instead** (`/v1/account/release_report`), whose `BALANCE_AMOUNT` is the available balance after each line, and syncs the last one in pesos as ARS cash, at medium confidence. The report covers the 7 days to the hour the read starts, so a retry within the hour finds the same report in the list: Plant asks for it (the adapter's one declared non-GET) only when the period is not listed, and waits when it is listed but not generated, within a 30 s budget like IBKR's, then fails for the job's retry. A file name that is not a plain `.csv` name fails the read. If Mercado Pago refuses the request because the account has no report configuration, the sync fails for good (`unsupported`, whose sync copy tells the user to follow the help, which says to generate the report once from Mercado Pago's Reportes); Plant does not create the configuration itself, as that is a write to the account's settings. `check` reads `/users/me`. The CSV is split by comma or semicolon, quotes holding separators and line breaks; amounts take a decimal point, and only in a semicolon report the es-AR form (thousands dots, decimal comma). The last peso line that prints a balance decides: if it does not read, there is no balance (never an earlier line's), and the draft counts it as skipped, as it does a zero or negative balance.
- **Bitso**: key and secret, signed with the hex HMAC-SHA256 of nonce, method and path; the nonce is Bitso's v2 (milliseconds plus a six-digit salt). Bitso has no endpoint that says what a key may do, so the user confirms it has only "View balances" and "View account information". **Trades are not read**: Bitso lists them only to a key with "Place orders", which the confirmation rules out.
- **Ripio Trade**: API token and secret key, signed with the base64 HMAC-SHA256 of the timestamp, method and the request's path without its query. Ripio has no endpoint that says what a token may do, so the user confirms its only access is "Read". Balances are free plus locked. **Statements and trades are not read**: trades are listed per pair (one request per market), and the statement's deposits and withdrawals have no operation kind in the review.
- **Institutions**: Roxom, Mercado Pago (or MercadoPago), Bitso and Ripio by the account's name. "Ripio" connects Ripio Trade; the Ripio app's balances come by statement, as the help says.
- **The prototype** syncs each with made-up holdings of instruments it knows; Mercado Pago's money stands as the money market fund it earns in, since the prototype has no cash instrument to sync.

## 2026-10-14 · Connectors: one port, Vault, Wallbit, IBKR, Nexo and IOL (PLA-155, PLA-156, PLA-157, PLA-158, PLA-160)

- **A provider is its adapter and its registry entry.** `packages/sources/src/connections` holds one `ConnectionProviderPort` per provider, made by `defineConnection` from its credential schema (key and secret, a single key, a token and query id, a username and password), `check` and `read`, plus what it reads (holdings, operations) and how its read-only is known. `connectionAdapters()` lists them; the web app's `PROVIDERS` gives each one its name, the institutions it is, its field labels and how to make the credentials, in Spanish. The card, the server actions, the job and the validation all read from those two. Every adapter runs the same contract tests against a fake server.
- **Credentials live in Supabase Vault**, as one JSON object per account, and `CONNECTION_SECRETS_KEY` is gone. A user writes them in `account_api_keys.credentials`, which a SECURITY DEFINER trigger moves into Vault before the row is stored (authorized from `auth.uid()` and the account being the caller's and open, never from the row) and leaves null, which a check holds. The row keeps the provider, a hint and `vault_secret`, the Vault secret's id (named without `_id`: it is no reference to an owned row, and Vault is outside public). Deleting the key, or its account, deletes the secret. Only the import job reads credentials back, through `public.account_credentials` (definer, service_role only), filtered by user, account and provider. Keys sealed under the old server key were deleted: they are connected again. `secret_ciphertext` stays, unused and granted to nobody, until a later migration drops it.
- **How each provider is kept to reading.** Binance says what a key may do and Plant checks it (unchanged). A Flex token of Interactive Brokers can only run the user's Flex queries. Wallbit and Nexo Pro do not say what a key may do, so the user confirms they made it with the `read` permission or the VIEWER role; a Wallbit answer that lists `trade` among the key's permissions refuses it. IOL has no read-only credential (Tomas accepted it): the user confirms they understand, and Plant asks for a token (the only POST) and calls only GETs. Every adapter's contract test checks it sends nothing but GETs and that declared login.
- **A sync reads holdings or operations**, never both: `imports.sync_draft` says which, so each lands in the review it already has. "Sincronizar" reads holdings; "Traer operaciones" shows where the provider gives them (Wallbit's trades, Interactive Brokers' executions and dividends). The prototype offers holdings only, as its review takes no operations.
- **Each provider's reading.** Wallbit: dollars of the checking and investment accounts added up, pesos kept, other currencies skipped, each stock by its shares; completed trades as purchases (dollars out) or sales (dollars in), at medium confidence, since the shape of a trade's two sides comes from Wallbit's examples. Interactive Brokers: each position's summary row with its mark price, value and cost basis, the cash by currency, dated as the statement; waits while IBKR generates it within a 30 s budget per read, requests included, then fails for the job's retry; its token, which Flex takes in the URL, is kept out of traces. Nexo Pro: each asset's total balance from `/accountSummary`; the savings and Earn balances of the main Nexo app are not in it and come by statement. IOL: the portfolio in Argentina with its last price, value and average cost, and each account's balance as cash. Figures that come as JSON numbers are taken to eight decimals.
- **A sync of operations reads a period the user picks.** "Traer operaciones" opens a dialog with *Desde* and *Hasta*, a year up to today by default, kept in `imports.sync_from` and `sync_to` for the job. The port filters every provider's operations to it, and IOL also asks its API for the period. The kinds are chosen in the review, not before reading: there the user filters by kind and asset, includes or discards the rows shown at once, and sees how many will be imported.
- **An operation is imported once, by the provider's number.** Each operation carries the provider's id as its `reference` (IOL's order `numero`, Wallbit's `uuid`, IBKR's `tradeID` or `transactionID`). The review marks one the account already holds under that number and does not offer to bring it back, and confirming discards it again on the server, so a second tab or an overlapping period writes nothing twice. One with no number is matched by day, kind, instrument and units, and the user decides.
- **IOL's operations**: executed buys and sells from `/api/v2/operaciones` (`filtro.estado=terminadas`), what IOL executed over what was ordered, the currency from the order or else its market; any other kind of order is skipped. Read at medium confidence: the fields come from IOL's documentation, not from an account that had operations.
- **A provider's institution**: Binance, Wallbit, Interactive Brokers (or IBKR), Nexo, and IOL (or InvertirOnline) by the account's name; the server refuses credentials for an account of another institution.

## 2026-10-14 · CEDEAR and bond quotes from IOL (PLA-161)

- **InvertirOnline is a fourth quote feed (`iol`), read with Plant's own account** (`IOL_USERNAME`, `IOL_PASSWORD`, server-only, set where `PLANT_RUN_JOBS` is). The composition root reads them and passes them to `quoteFeeds`; core reads no environment. Unset, the feed fails `unconfigured` (a new non-retryable `QuoteFeedError` code) before any request and the other feeds run as usual, so the run ends `partial`.
- **Two requests per read, one per panel**: `GET /api/v2/Cotizaciones/{cedears|titulosPublicos}/argentina/Todos`, rather than one `Titulos/{simbolo}/Cotizacion` per symbol. Each line's `ultimoPrecio` is the price and `fecha` its instant, read as Buenos Aires time when it carries no offset. A panel that fails lists each of its instruments as unread with the code; the other panel is kept.
- **The symbols are a fixed list in the adapter, as Kraken's are**: the catalog's seven CEDEARs and three bonds, and a test fails when a CEDEAR or bond is seeded without being on it, or the list names one the migrations do not seed with that type and currency. `service_role` keeps reading nothing of `instruments`. There are no stocks in the catalog yet.
- **A dollar instrument is read from its MEP line** (`GD30D` for GD30), so its price is in dollars as the catalog keeps it; a line whose `moneda` is unknown or names the other currency is refused, and a dollar line is priced only when its `moneda` says dollars. **A bond's price is per 100 nominal and stored per unit** (`exactUnitPrice`), so AL30 at 71500.5 is stored as 715.005; a price 8 decimals cannot hold is refused.
- **BYMA closes on the weekend, so Friday's price read on Saturday or Sunday is `closed`**, like the dollar's, instead of `stale`; prices from `iol` use a `listed` window. A weekday line dated another day (a holiday, or a symbol that did not trade) is `stale`. A missing line, one with no positive price or with an unreadable stamp is invalid.
- **The token is fetched inside the read**: a password grant, kept in the feed for its life (15 minutes, renewed a minute early), then a refresh grant while the refresh token lives, falling back to the password when IOL refuses it. A cached token IOL refuses with a 401 or 403 (`unauthorized`, a new non-retryable code `feedErrorForStatus` gives those statuses) gets one more try with a new one; any other 4xx fails its panel. The panels are read with an 8 MB body cap (`GetJson`'s `maxBytes`); the other feeds keep 2 MB. Neither the token nor the credentials leave the read: errors are codes, steps return counts and keys.

## 2026-10-14 · Price alerts in the app (PLA-154)

- **An alert is on a dollar's sell rate (MEP, CCL, official or blue, in pesos) or an instrument's price in its currency, above or below a figure**, and it fires once: the quotes job marks it met with the quote's day and price, and it waits no more. The user sets a new one for the next figure.
- **A gain alert is on an instrument the user holds: it gains (or loses) a percent over its average cost.** The cost is the open lots' (FIFO), in the currency the instrument is quoted in, as Activos works it out; the alert stores it and the price it means. Both are worked out again after every write that changes movements (an operation, a holding created or deleted, an import confirmed), so the figure follows what the user holds; a lot whose cost has no value in that currency leaves the alert waiting with no figure, and the page says so.
- **A quote is the feed's or the user's own manual price or rate up to today, the newer one winning** (the manual one on the same day), as the valuation does: today only crypto and the dollars have a feed, so a bond or a CEDEAR is watched through the prices the user enters.
- **The latest quote counts, whenever the alert was set**, so one that is already met is marked on the next run, as the prototype marks it when it is set; its day is never before the day it was set.
- **The quotes job checks every alert in one SQL statement** (`meet_price_alerts`, SECURITY DEFINER, only the service role runs it) after it saves the quotes and before it writes its run line. A failure is logged and the alerts wait for the next hourly run; the quotes run keeps its outcome.
- **Alerts show on Resumen until the user marks them seen**, not in a header bell: the header sits outside the data pages' prototype, and Plant has no mail or push channel yet. They are set and deleted in Ajustes, 50 at most, which a trigger enforces under a lock on the user.

## 2026-10-14 · Binance by API, first slice (PLA-65)

- **One exchange, Binance, and only its spot balances.** An account whose institution is Binance offers "Conectar Binance" on its page, and the server refuses a key for any other account; any account holding a key shows it. Earn, futures, funding wallets, trades and other exchanges or brokers wait for later slices.
- **A sync is an import, not a write.** "Sincronizar" inserts an import that names its account and exchange instead of a document (`imports.document_id` became nullable, with a check that an import has exactly one of the two), and the import-document job reads the balances into the same draft a file yields, so the review and confirm flow is the same one. Nothing writes holdings directly.
- **A sync counts against no quota**: it costs no model. The database allows one sync in flight per account, and only on an open account with a key of that exchange. "Sincronizar" on an account whose sync is still queued sends its job again (the event's id is the import's, so it runs once) instead of starting another, so a job that was never sent does not lock the account. A sync that fails says so about the exchange, not a file.
- **Only read-only keys.** Before storing a key and again on every sync, Plant asks Binance what the key may do (`/sapi/v1/account/apiRestrictions`) and refuses one that cannot read, or where any field but `ipRestrict`, `createTime`, `tradingAuthorityExpirationTime`, `enableReading` and `enableFixReadOnly` is anything but literally `false` (trading, withdrawals, transfers, margin, futures, options, or a field Binance adds later), as `connection_not_read_only`. Plant calls only signed GETs.
- **Keys are sealed at rest with AES-256-GCM** (superseded by Vault, see PLA-155) under `CONNECTION_SECRETS_KEY`, a server key (32 bytes, base64), bound by the additional data to the row's user, account and exchange, so a sealed key copied to another row does not open. `authenticated` inserts, replaces (one UPDATE, so a failed write keeps the old key) and deletes a key but never reads the sealed column (a column grant; a GET names its columns); only the import job reads it, as service_role filtered by the user and the account. The key and the secret are never logged or sent back; the page shows the key's last four characters.
- **Every balance is a USD row with no price**: free and locked units added up, confidence high, the review prices it as it prices a file's. An asset Binance names that Plant does not know (an Earn position as `LDUSDT`, a token) is left for the review to match or discard, like an unknown symbol in a file; a balance too large for a quantity is skipped and counted.
- **The prototype fakes the exchange**: any key connects except one with "TRADE" in it, which stands for a key that can trade; a sync reads made-up balances of BTC, ETH and SOL.
- **Connecting asks for no recent second factor**, as uploading a statement does not: the key only reads, and the session already passed the MFA gate.

## 2026-10-14 · Impuestos: Bienes Personales and Ganancias estimates (PLA-66)

- **A page, Impuestos (`/taxes?year=`), computed from the data the closes already read**: no migration and nothing stored. It opens on the last year that ended (the one being declared) when there is data for it, else on the one in progress, and offers every year from the first movement's. The year in progress is valued at today and says so.
- **It is an estimate, not tax advice, and says so first.** The rules are deliberately simple and listed on the page; it computes no tax due, no non-taxable minimum, no deductions and no rates, which change every year and depend on the person.
- **Bienes Personales values what was held at the end of December 31** as the closes value that day (each instrument at its quote of the day or the last one within a week, else its last trade price), a foreign-currency asset at the **official buying rate** (`fx_rates` kind `official`, column `buy`, from DolarApi's Banco Nación rate) of that day or the last one within a week. That rate is read apart: the valuation snapshot only carries selling rates. With no buying rate, dollar assets show no value and the totals say a figure is missing. The prototype's made-up quotes have no buying rate, so it takes the official selling rate less $ 40.
- **Exempt, simplified**: plazos fijos (deposits in an Argentine bank) and bonds (the `bond` type covers government bonds and corporate notes, both exempt). Cash, CEDEARs, FCIs, crypto, real estate and other assets count as taxable; cash in an Argentine bank may be exempt, and the page says so rather than guessing where it sits. The real app keeps no placement kind, so every fixed-term placement there counts as a plazo fijo, and the page says so and asks the user to add a caución or a loan to the taxable total by hand; the prototype excludes cauciones, loans and other placements. Real estate and other assets go at the value the user stated, not their fiscal valuation. Debts are not subtracted.
- **Holdings with no history (cash, placements, real estate, other) count with today's amount in past years**, as the closes do; a placement that started after the year's end is left out.
- **Ganancias adds up the year's realized results in pesos, by kind**: sales by instrument type, with the ledger's result (the oldest units first, less charges), and dividends, coupons and yields (staking, earn), before withholdings. Each movement is in pesos at its own day's rates, as every view in pesos computes it. It does not split exempt from taxable income: that depends on each asset and the person.
- **The report leaves out what the user left out**: every holding of an account with "incluir en el reporte impositivo" off, and an asset in `tax_report_exclusions` (an instrument across every holding of it, or one holding), in both sections. The page counts the assets held that day it left out, and points to where that is changed: the account, and the asset only in the prototype, since the real app has no per-asset toggle yet. A yield that takes units out counts as the ledger books it: their value that day lost, plus what they had gained over their cost.
- **Each section downloads as a CSV**, and the page saves as a PDF through the print dialog, as Resumen does.

## 2026-10-14 · Assistant scenarios and month summaries (PLA-70)

- **A scenario moves today's quotes and nothing else.** `simulateScenario` scales one dollar's sell rate (MEP, CCL, official, or all three), one instrument's price or every price by a percent between -99.99 and 1000, and revalues the open holdings and the debts at today's quotes as Resumen does. A peso price that follows the dollar in reality (a CEDEAR) stays where it is; the tool's note says so, and the answer opens with "Hipotético:". An instrument the user does not hold, or has no price for today, is refused rather than "moved", and a dollar nothing they hold or owe is valued at is reported as changing nothing.
- **A month's change splits into what was put in, prices, the dollar and yields**, which add up to the change exactly. The dollar's part is the month-end holdings and debts at end quotes less the same at end prices with the start's dollar rates; prices take the rest of the closes' market result. A CEDEAR's peso price that rose with the CCL therefore counts as price in pesos. Income paid out (without yields, which are their own part) and charges are listed apart. Several consecutive months add up month by month.

## 2026-10-14 · A workbook's unzipped size is capped (PLA-142)

- **A zip workbook is measured before SheetJS opens it.** An XLSX is a zip, and SheetJS unzips every entry into memory before the row limit applies, so a small upload could exhaust the function. `readSheet` walks the zip's central directory as SheetJS 0.20.3 does (the last end record) and refuses it as `unreadable` past 1000 entries or 50 MB unzipped in all, when the directory or a local header is cut or out of the file, when an entry's local header declares other sizes than the directory, and for ZIP64. - **SheetJS is pinned to 0.20.3, installed from its CDN tarball** (`https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`), which `pnpm audit` does not check. Its advisories are read at https://git.sheetjs.com/sheetjs/sheetjs (issues and the changelog) whenever the tarball is bumped, and the zip check above is reviewed against the new version's reader, since it mirrors how 0.20.3 unzips.

## 2026-10-13 · What the browser reports (PLA-88)

- **One endpoint, `/api/reports`, outside the proxy and without a session**, takes CSP violations (`report-to csp` and `report-uri`, from `Reporting-Endpoints`) and the app's own reports of failures only the browser sees. Each becomes a `browser.csp` or `browser.error` warn line.

## 2026-10-13 · Movements, manual prices and the report in the database (PLA-103, PLA-104, PLA-122)

## 2026-10-13 · Sale cost by first in, first out (PLA-128)

- **Every unit outflow takes a holding's oldest units first, each at its own cost** (FIFO, PEPS). - **"Costo prom." stays the cost of what is held over its units**, which FIFO now makes the cost of the open lots.

## 2026-10-12 · Period yields (PLA-123)

- **A "Rendimiento" is units of an instrument holding earned or lost without money in or out** (staking, earn, trading results), in the holding's own units, each valued at what it was worth that day. It is one portfolio's, has no charges, and never starts a holding: only a holding that exists earns, so admission refuses a history that would start with one, including after deleting what came before it. The store lets one reopen a holding sold to zero (staking paid after a sale); the prototype lists no closed holding to load it from yet. A loss is refused past what was held, like any sale. Instruments only: cash has no movements yet.
- **Its value is the period's return, never a contribution.** Units in add their value to the holding's cost and to its income; units out leave with the cost of the oldest lots, take their value off the income, and realize what they had gained over that cost. Its cash flow is a yield: the returns count it in the value, not as paid in or out, and a close counts it as income and keeps it out of the market move and of the money at work.
- **The realized tile reads "Resultado realizado"**: what sales made and what units a loss took out had gained. The sales tab lists sales only. Income tiles read "Dividendos, cupones y rendimientos"; the close's note and the assistant call them rentas.
- **The value per unit is the quote of that day in the instrument's currency** (the feeds' latest within their carry window, else the user's latest manual price on or before it), shown as "Sugerido"; the dialog sends what it shows, so a stored yield always has its value, and with no quote the user types it. A close values a day nothing quotes at the latest day's purchases, sales and yields on or before it.
- **"El saldo final" records the difference** between the balance the user types and what the holding held at the end of that day (an edit counts without the yield it replaces), as a yield in or out; the same balance is refused. A yield given as a balance goes last on its day, new or edited, so the balance is what the day ends with. The rule lives in the prototype's write; it moves to core with the real write path (PLA-103).
- **The kind is named "Rendimiento"**, beside "Rendimiento anual (TIR)" on the instrument page; the list shows a loss as "Rendimiento negativo".

## 2026-10-12 · Transfers between portfolios (PLA-118)

- **A value the app computes or fetches (a cost, a price, a market value) shows as a suggestion the user can change.** Left as suggested it follows the data; changed, it is the user's.
- **A "Traspaso" moves units of an instrument from one portfolio's holding to another portfolio's holding of it in the same account**: one operation with a side out and a side in, of one quantity, with no charges (a fee since PLA-140). It is no money in or out (a flow of 0 in closes and returns) and makes no result.
- **The units arriving carry the cost the units leaving took**, worked out when the holdings are replayed, so an edit to the first portfolio's earlier history reaches the second, in every unit. The dialog shows that cost per unit as "Sugerido", worked out by running the write and throwing it away, so it is what saving carries; a cost the user types instead is fixed, and the difference shows as unrealized until those units are sold, then in that sale's result.
- **One account's holdings of an instrument replay together** (every account's since PLA-125), in date and entry order, a transfer's side out before its side in, and a write reloads all of them. A holding's history is not resumed from a stored step, since a transfer's cost comes from another holding.
- **A holding with a transfer cannot be deleted** ("Tiene traspasos con otra cartera…"); the transfer is deleted first, from its movements, with both sides. An edit to the first portfolio still reaches a second one that is closed or archived. A write to an archived account or portfolio, or one that would leave units open in one, is refused with the restore message the holding dialog uses. When movements persist (PLA-103), the holding-to-movements cascade becomes a guard for transfer sides and `holding_has_transfers` joins the setup guard's hints.

## 2026-10-12 · Entry order within a day (PLA-116)

- **Within a day, an opening balance comes first and the rest go in the order their operations were entered.** Every movement carries its operation's `entry_order` (all its parts share it, and the store's integrity test checks that); a new operation takes the next one. So a buy-back on the day of a sell-out opens a new cost, and a purchase entered before a sale that day can be sold (dollar MEP). Ordering by kind folded a same-day buy-back into the sale's average cost.
- **An edit on the same date keeps its operation's place.** One that moves the date, or turns an opening balance into another kind, goes last on the day, as if entered again (moving it back puts it last again; an opening balance has no place of its own, it is what was held before the day), unless going last would take out more than was held or leave the holding not starting with units coming in; then it keeps its place. When neither place works, the remedy is to delete and re-enter in order: a third place, first in the day, would need a fractional order for a case the order of entry already answers. The refusal copy says that the order within a day counts.
- **When movements persist (PLA-103), the entry order is a per-user number the server write path assigns**, never a Postgres sequence and never writable by `authenticated`.

## 2026-10-11 · Debts and net worth (PLA-113)

## 2026-10-11 · Resumen and closes (PLA-112)

- **A month closes by itself when it ends; there is no close button.** Its close shows net worth at its start and end, what came in (purchases, opening balances and adjustments in, before charges) less what went out (sales and adjustments out), the market result (the change not explained by money put in or taken out or by yields (PLA-123), so from prices and the dollar alone), dividends, coupons and yields before withholding, charges (commissions, fees, taxes and withholding), what it realized (PLA-123), and the month's return without contributions (modified Dietz: market plus income less charges, over the money at work, money in weighted from the start of its day and money out from the end of it, since it worked the day it left; income is what the money made, not money put in). An opening balance brings in units already held, and an adjustment out takes units away, at their exact worth that day (at their cost when unpriced), so neither the gain they carry nor their cost shows as the month's market result; the price stays their cost for sales. A month with nothing at work and nothing made returns 0, so an empty month after a sell-out does not blank the year. A year is the sum of its months, its return their chained returns. A close that left out a holding without a price, a movement its unit cannot express, or an opening balance or adjustment out unpriced on its day is marked "Parcial"; a month whose return cannot be measured (it made something with no money at work, a large early outflow left none, or it lost more than the money at work) has no return of its own and the year's leaves it out, marking the year "Parcial"; a first purchase counts from the start of its day; closes are in pesos and dollars only, since a movement carries its date's dollar rates, not Bitcoin's price.
- **A closed month whose figures or movements a movement write changes is recalculated and marked** "Recalculado el dd/mm/aaaa"; nobody reopens it. A write moves no quote, so what is compared, in every unit closes are shown in, is the month's figures to the cent (its start and end values, what came in and out, income, charges and what it realized), its own movements and the units held at its end, per account and instrument, so moving units between portfolios marks nothing. A write that changes no movement marks nothing, though past values move with it: a price, or a holding with no movements, which counts today's amount on every past day until holdings have a history. A month's detail shows an opening balance or adjustment out at what it was worth that day, as its figures count it, with no price and a note saying so.
- **Past values in the prototype:** an instrument holds what its movements left by that day, at that day's price, or a manual price on or before it, or else the price of its latest trading day, that day's purchases, sales and yields averaged by their units (an opening balance's or adjustment's price is a cost, not a trade's); every other holding counts today's amount on every past day until they have a history.
- The home page's Supabase status, a dev aid, is gone: outside production Resumen shows the prototype.
- **The close pages (`/closes/[period]`) have no real version yet** and call `notFound()` in production. Their links keep the unit the user chose.

## 2026-10-10 · Holdings and valuation (PLA-25)

- **`instruments` is a global reference table that nobody writes.** Its migration seeds the symbols the quotes job prices (BTC, ETH, SOL, USDT and USDC, as crypto in USD); `authenticated` reads it and no API role writes it, `service_role` included. A new symbol is a migration. Crypto only for now: CEDEARs, bonds and FCI arrive with PLA-28 and PLA-39. The pgTAP floor's reference-table exception now lists three tables, and core tests that every priced symbol is seeded with its currency.
- **A holding is one row per asset class, and `amount` means what the class says.** `asset_class` is `instrument` (units of `instrument_symbol`, priced from `prices`), `cash` (an amount in `currency`), `fixed_term` (the principal in `currency`, with `annual_rate`, `started_on` and `matures_on`), `real_estate` or `other` (a value in `currency` as of `valued_on`). A `CHECK` with one branch per class requires its columns and nulls the rest, except an optional label on cash and fixed terms; core's holding schema mirrors it, and tests read the branches and the rate bound from the migration. `amount` is `numeric(20, 8)` and positive; `annual_rate` is a fraction between 0 and 10 (1000% a year); dates fall between 1900 and 9999, so every stored date parses as an ISO date.
- **A holding belongs to one of the user's accounts and portfolios**, through composite foreign keys like accounts (`23503` with no hint for another user's id or a random one, active or archived, or `23502` when the portfolio is left to the default). With no portfolio, a `BEFORE INSERT` trigger puts it in its account's default portfolio. An account's portfolio holds one active position per instrument (a partial unique index), so a double submit or a retried import cannot count it twice; the same instrument can sit in two portfolios of one account. Cash, fixed terms and other assets may repeat, told apart by their label.
- **The guards keep every active holding in an active account and portfolio.** Archiving an account or portfolio that an active holding uses is refused (`source_connection_has_holdings`, `portfolio_has_holdings`); creating, restoring or moving an active holding into an archived one is refused (`source_connection_archived`, `portfolio_archived`). The holding triggers take the portfolio-setup lock only on insert and on an update that sets `portfolio_id` or `archived_at`, so editing an amount does not wait on it. A holding is archived, never deleted. The holding guard keeps its own copy of the archived-portfolio rule the account guard applies, since a trigger cannot call a helper in `private`; a third table with the rule (debts, PLA-77) moves it into one shared trigger function.
- **An instrument is keyed by its bare ticker**, like `prices.symbol`. A ticker listed in two markets or currencies (a CEDEAR and its US share) needs a market in the key; that change comes with the first such instrument (PLA-39) and rewrites `holdings.instrument_symbol`.
- **Deferred to PLA-28:** `transactions` and its reconciliation with `amount`, where a holding came from (manual or an import), the quote snapshot reader and the holdings read.
- **Valuation lives in `@plant/core` and is pure.** `valueHoldings(holdings, snapshot, { denominator, referenceDollar, portfolioId? })` values each holding and sums them, all portfolios or one. A server that reads holdings and a `QuoteSnapshot` (each rate and price with its own date) calls it; PLA-27's daily job pages users by keyset and calls it per page.
- **A denominator is an entry in `DENOMINATORS`**: `ars`, `usd_mep`, `usd_ccl`, `usd_official` and `btc`. A dollar unit carries its rate kind, and BTC is priced through USD MEP (`priced: "BTC"`, `via: "usd_mep"`). Adding a unit is a member of `Denominator` and an entry; one held as money (EUR) also needs its currency and rate kind. BTC values are not `Money`, whose currency is ARS or USD: a value is an exact amount with its denominator.
- **One dollar per view, on the sell side in both directions.** A view picks its reference dollar (MEP by default, CCL optional), and a dollar held is worth that dollar: in a USD view a dollar is one, and in pesos it is the reference rate. Converting between units (`convert`) goes through pesos at each unit's own rate, so 1 USD MEP is 1200/1250 USD CCL; between a unit and the one it is priced in (USD MEP and BTC) it uses the price alone, so dollars shown in BTC need no rate and are dated by the BTC price. A held dollar keeps its face value in every dollar view and reaches BTC through USD MEP whatever the reference, so in a dollar view other than the reference, or in BTC under a CCL reference, it differs from the rate between those units; tests pin both rules.
- **Arithmetic is exact and rounds once.** Amounts become gcd-reduced fractions of `bigint` (`Exact` in `@plant/shared`), every step stays exact (except a fixed term's interest, credited in cents), and the value is rounded once, half away from zero, at the denominator's scale (2 digits, 8 for BTC). The total is the rounded exact sum, not the sum of rounded items; the items still reconcile with it within the rounding. `costUsd` reuses the same rounding.
- **A fixed term earns simple interest, actual/365**, from `started_on` to the snapshot's date, capped at `matures_on`. Before it starts it is worth its principal; from its maturity date on it is worth principal plus all its interest and is marked matured.
- **A missing quote is reported, not guessed.** A holding whose price or rate is missing is left out of the total, which says `complete: false` and lists the missing holdings' ids; a value is never priced at 1:1 or at cost. Every value carries `asOf`, the oldest of the holding's own date and the quotes it used, so a stale rate shows. The caller passes only active holdings: a holding carries no `archived_at` here.
- **Tests read the migrations through `@plant/shared/testing`**, a test-only export; ESLint fences every package's `testing` subpath (also `@plant/jobs/testing`) away from runtime code. The parity tests in shared, core and web (guard hints, the class `CHECK` and rate bound, the symbol pattern and seeded symbols, the quotes guards' time zone and SQLSTATE) use it.

## 2026-10-09 · Daily quotes job (PLA-93)

- **Local only for now.** `refresh-quotes` registers only in dev-server mode (`DEV_SERVER_MODE` in `@plant/jobs`, from `NODE_ENV === "development"`, so only under `next dev`), because staging and production share one database until the beta. `createServeOptions` builds the job's dependencies, and with them the service-role client, only when it registers it. The job writes wherever `next dev`'s Supabase env points: `pnpm dev:up` always rewrites `.env.development.local` to local Supabase, and Vercel's Development environment never holds `SUPABASE_SERVICE_ROLE_KEY` (`.env.example` says so). Registering it on a deployment is part of PLA-73.
- **Hourly from 18:05 to 23:05, Buenos Aires time** (`TZ=America/Argentina/Buenos_Aires 5 18-23 * * *`, from `BUENOS_AIRES_TZ` and `QUOTE_CLOSE_HOUR`), since MEP and CCL close at 17:00. A later slot fills a slot missed while the machine slept, a source down past its retries, or a dollar house a day behind; the first insert of the day wins and later runs insert nothing. The 23:05 slot has none after it, so a house that fails there leaves the day without its row. `singleton: skip` drops a run that starts while another runs, a manual `plant/quotes.refresh` event included, and a skipped run writes no line.
- **One step per feed that reads and then saves**, so a retry reads the feed again; that is also how the guard's `PT403` at midnight is handled (`out_of_window` is retryable), and a `PT403` on the last attempt ends the feed as failed. Two retries per step. One dolarapi house that fails is recorded as unread and retried by the next slot; a whole feed that fails is retried by the step. Quote rows never cross a step boundary: a step returns counts, keys and its time only, because in dev mode the memoized step output is whatever the caller sends. Forged output can only put strings on the run line (local logs only); the database only gets rows the feeds read.
- **Core classifies every row.** Each refused row's key lands in one bucket: `early` (a traded row read before the close hour), `closed` (Friday's dollar rate read on Saturday or Sunday), `stale` (any other date) or `invalid`. UVA, a daily index, is due at any hour and every day. The classification reads Buenos Aires' calendar, never the host's zone (core's lint bans the host-zone `Date` accessors and its tests run in Buenos Aires time). There is no holiday calendar: a weekday holiday, and the weekend after a Friday holiday, warn as `stale`.
- **One `quotes.refresh` line per run**, with `plant.outcome`: `failed` (every feed failed, at error, and the run is not retried), `partial` (a feed failed or a row was invalid, at warn), `stale` (a stale key, at warn), else `ok` (at info); `early` and `closed` keys never change the outcome. It carries the run id, the rows inserted, the keys of each bucket, the unread houses as `kind:code`, the failed feeds as `feed:stage:code`, and `duration_ms`, the work time of the steps that returned. Each failed attempt writes its own `quotes.feed_failed` line with the attempt, stage and code, and the store's own code (`plant.quotes.store_code`) when it gave one. Every key is bounded by an enum, the symbol pattern or a code list. A business day with no successful slot leaves no dollar row and no line says so; valuation reads the latest row on or before a date. A store left unconfigured goes unseen on a run that kept no rows.
- **The run line is at least once**: a lost run-complete checkpoint emits it again, so dedupe on `plant.inngest.run_id`. It is the run's wide event until a root span lands with the Dash0 export. The counts are what the attempt that answered inserted: a retried step that had committed counts 0 on the retry, or only the rows it added, and a dev-UI "rerun from step" gets a new run id and restates the original run's counts and keys for the memoized steps.
- **The store is a port.** `QuoteStorePort` and `QuoteStoreError` live in core beside the feeds; the PostgREST writer and its sink live in `apps/web/src/lib/quotes`, and only the Inngest route may import the sink. The writer upserts with `ignoreDuplicates` on each table's primary key (`QUOTE_KEYS`, pinned to the migration) and maps PostgREST's answer to a store code: `timeout`, `unavailable` (may have committed), `out_of_window`, `forbidden`, `invalid_row` or `rejected`. The HTTP reader times out after 10 s, follows no redirect (a 3xx is `http_4xx`) and refuses a body over 2 MB.
- **The amount columns refuse NaN** (`fx_rates_not_nan`, `prices_not_nan`, and `ai_costs_not_nan` on the same rule): Postgres's `numeric` takes `'NaN'`, which passes `> 0`, `>= 0` and `<=`. `Infinity` does not fit `numeric(20, 8)`.
- **`next dev` and the Inngest dev server bind 127.0.0.1**, because dev mode checks no Inngest signature: another device on the network could otherwise run the job. In dev mode the app registers at `http://127.0.0.1:3000` (`serveOrigin`) whatever Host a request sends, so a page rebinding its DNS to loopback cannot move the job to its own host, and `next dev` is pinned to port 3000, so it fails rather than move to another port while the app still registers at 3000. The dev server's connect gateway and gRPC ports cannot be bound in `inngest-cli` 1.46.0 (see the Inngest threat model).

## 2026-10-09 · Portfolios (PLA-95)

- **"Portfolio setup" is the user's portfolios, and from PLA-24 their accounts.** It names the shared pieces: the module `lib/portfolio-setup`, the log events `portfolio_setup.*`, the advisory lock key and `PORTFOLIO_SETUP_GUARD` in `@plant/shared`. "Cuenta" is UI copy; in code "account" stays the user's Plant account, except for the `/accounts` route.
- **Every user has at least one active portfolio.** Signup inserts "Principal" next to the profile (`private.create_profile_for_new_user`), and the migration gave every existing user one. Users archive portfolios and never delete them: no API role holds `DELETE`, and a portfolio goes only with its account (cascade). An archived name can be reused by an active portfolio. `archived_at` is the server's time the row was archived, kept when an archived row is archived again; the client only says whether a row is archived.
- **The guards are triggers that key on the row's `user_id`, never on `auth.uid()`**, because the signup function, the seed and the table owner write past RLS. They hold on archiving: no API role can delete a portfolio or move it to another user, so an owner script that does must keep each user one active portfolio itself. A guard refuses with `PT409` (PostgREST answers 409) and a hint from `PORTFOLIO_SETUP_GUARD.hints`, which the app maps to its copy; `PT403` stays the quote guards' code (PLA-26). PLA-24 adds the account hints, and PLA-25 extends the portfolio guard to portfolios that still hold holdings, with an index on `holdings (user_id, portfolio_id)` for it.
- **One user's writes to the portfolio setup are serialized** by a transaction-level advisory lock that the first trigger takes on every insert and update, so a guard counting rows sees every committed write of that user. This holds under READ COMMITTED, the isolation every API request runs at; a writer at REPEATABLE READ would need the guard to lock the rows it counts. A data migration that touches many users' rows disables `portfolio_setup_1_lock` in the same transaction as its writes (the `ALTER TABLE` then blocks every user's portfolio writes until commit) or commits per user, since each row holds its user's lock until commit. A statement that updates several rows can deadlock with a concurrent one (row lock, then advisory lock) and fail with `40P01`; the app updates one row per statement, and a later writer that changes several of a user's rows in one transaction first locks all of them, in id order, with `SELECT ... FOR UPDATE` before its first write.
- **Every write is a server action in `app/(app)/(data)/accounts/actions.ts`**, through `runInsert` or `runUpdate` (`lib/portfolio-setup/run-write.ts`): the session's claims (its redirect propagates), zod on every argument, the write with the user's JWT filtered by `user_id` and the parsed id besides RLS, one `portfolio_setup.write` line, and `revalidatePath("/accounts")` on every outcome but invalid input, so a write that failed after committing shows before the user retries. An update must change exactly one row: none is `not_found`. A refusal maps to the copy in `messages.ts` through `toWriteResult`, which reads a guard's hint only against `PORTFOLIO_SETUP_GUARD.hints`. The line carries the action, outcome, row id and duration, never a name or PostgREST's text, which carries the row. A restore whose name an active portfolio took asks for a new name and renames and restores in one update. Names are trimmed, normalized to NFC with single spaces and without a variation selector after an emoji that already shows as one (so two names that look the same collide in the unique index) and refused with control characters, lone surrogates, format characters or any default-ignorable code point outside an emoji-shaped sequence (soft hyphen, zero-width space, bidi marks, a variation selector, joiner or tag anywhere else), blank fillers and symbols, or nothing visible (two look-alike emoji sequences can still be distinct names); the table's CHECK only bounds the length and outer spaces, since a name is only ever shown to its owner.
- **The page lists up to 300 active portfolios and pages the archived ones by keyset**, 50 at a time (`lib/supabase/keyset.ts`): the cursor is the last row's `archived_at`, kept as the text PostgREST returned so no microseconds are lost, and its id, both validated before they reach a filter. An invalid cursor shows the first page and logs a warning. A failed read logs one `portfolio_setup.read` line naming the list that failed (`active`, `archived` or `both`) and throws a `LoggedError`, which the error page shows with a retry and `onRequestError` skips, so one failure is one line.

## 2026-10-09 · Turning MFA off and the step-up (PLA-76)

- **Turning TOTP off is the first sensitive action.** The switch in Ajustes opens a dialog. Without a sign-in by mail or Google in the last 15 minutes (`needsStepUp()`, the same rule as `requireSensitiveSession`), it first asks the user to sign in again; otherwise it asks for a current code, verifies it in the browser and calls the server action `disableTotp(factorId)`. The action runs `requireSensitiveSession("disable_mfa")`, then `unenrollForSession` (`lib/auth/mfa-disable.ts`) checks that the session verified a TOTP code in the last two minutes (`totpIsFresh`), that Auth's user is the session's and that the factor is one of that user's verified factors, removes every verified factor with the verified one last (Auth drops a session to `aal1` when the factor it verified is removed, and an `aal1` session cannot remove another), and refreshes the session so the next token says the user has no factor. The server decides both rules; the dialog's first screen only saves typing a code the server would refuse, and an answer of `sign_in_again` switches it to the sign-in screen.
- **No separate re-authentication screen.** The step-up signs out on this device and sends the user to `/login?next=/settings?confirm=disable`; an enrolled user then passes `/auth/mfa` as on any sign-in and lands back in Ajustes with the dialog open, where they type a code again although `/auth/mfa` just took one (the server would accept that one for its two minutes; the dialog cannot tell whether it is still fresh). A dedicated screen would repeat the sign-in for the same proof. Signing out first keeps the old session from outliving the proof beside the new one; if the mail does not arrive, the user waits for it like any sign-in. `?confirm=disable` only opens the dialog.
- **The server unenrolls, the browser verifies.** Auth rate-limits verify and challenge per caller IP, so the code stays in the browser; the unenroll runs on the server behind the gate. Lint lets `mfa-disable.ts` call only `mfa.unenroll` and keeps server actions out of it, since it trusts its caller to have run the gate. An `amr` timestamp ahead of the server's clock counts as recent: the token is signed, so it is clock skew.
- **`auth.mfa.disable` logs one line per call**, with the request id, the user id, the outcome and the counts of verified and removed factors, never a code or a factor id: `disabled`, `totp_stale` and `session_ended` at info; `factor_not_found`, `user_mismatch`, `invalid_input` (a non-string id, before the gate and without a user id) and `session_refresh_failed` at warn; `partial` (factors left behind) and `error` (nothing removed) at error, with Auth's error; the other outcomes Auth caused carry its `error.type`. A refusal at the gate is `auth.step_up` with `disable_mfa`. The audit rows of part 1 record each factor removed and the sessions the step-up's sign-in and verify create and delete.
- **As with email change, the gate holds for Plant's UI, not for a direct call to Auth**, which lets any `aal2` session unenroll its user's factors.

Quotes are market data that valuation reads, so the feeds live in `core`, not in `sources`, which holds the user's portfolio sources. - **Only today's row may be inserted.** A `BEFORE INSERT` trigger per table refuses any date other than today in Buenos Aires with `PT403` (PostgREST answers 403, which lets the writer in PLA-93 tell it apart from a missing grant, `42501`), because a past or future row would never be replaced. It fires before `ON CONFLICT`, so a past duplicate is refused too. The table owner corrects a row with `UPDATE` in a migration, and a history backfill (PLA-25) disables the trigger and enables it again inside its own migration, as does a data restore of past quotes. The two guards repeat the rule on purpose, since `fx_rates` may get a rule per kind; a third table with the same rule gets one shared trigger function. pgTAP pins the guards' `America/Argentina/Buenos_Aires`, and core's migration test that it matches `BUENOS_AIRES_TZ` in `@plant/shared`.
- **The pgTAP floor's reference-table exception**: a public table without `user_id` must be `fx_rates` or `prices`, its permissive policies may only let `authenticated` read every row, `authenticated` may not write it, `service_role` may not update or delete it, and it has no foreign key, since every user reads what a row points at. No table inherits from it, since a child's rows reach every reader past the guard. The owner predicate and the owned-table asserts skip those two; the MFA gate does not. PLA-25 adds `instruments` as a third.

- **Four more `audit_log` actions, all from database triggers:** `auth.session.deleted`, `auth.mfa.verified` (a session raised to `aal2`), `auth.mfa.factor_verified` and `auth.mfa.factor_removed` (a verified factor deleted). Enroll, verify, unenroll and sign-out run between the browser and Auth, so only the database sees all of them. An unverified factor, a refresh and a failed TOTP attempt write nothing, and a TOTP verify on a session already at `aal2` (a step-up) writes only the `auth.session.deleted` rows of the sessions below `aal2` it deletes; Auth's logs keep the failed attempts.

## 2026-10-09 · MFA rules, part 2: the database gate and the app's checks (PLA-18)

- **Every `public` table has one RESTRICTIVE policy, "Requires two-factor authentication", for `authenticated` on every command**: the token is `aal2`, or its `mfa_enrolled` claim is `false`. A token without the claim counts as enrolled, so it reads and writes nothing below `aal2`. It overlaps part 1's `authenticated_aal1` role on purpose: the role covers what the hook demotes, the policy covers a token the hook never saw. A new table copies the policy verbatim (it is in `enforce-owner-isolation`'s house form): the pgTAP floor fails on a `public` table without exactly one RESTRICTIVE policy with that name, role, command and expression. ## 2026-10-08 · CSP and security headers (PLA-19)

- **`proxy.ts` sends the CSP, with a fresh nonce on every request.** Next reads the nonce from the request's CSP and stamps it on its own scripts; the root layout passes it to `ThemeProvider` for next-themes' inline script. Reading the request makes every page dynamic, which a nonce needs: a static page is built with no nonce, so the CSP would block its scripts.
- **`script-src 'self' 'nonce-…'`, no `'strict-dynamic'`.** Every script Plant loads is its own; `'strict-dynamic'` would let any nonced script load others from anywhere. `'unsafe-eval'` only under `next dev`, which needs it. The e2e fails if production allows eval.
- **`style-src 'unsafe-inline'`.** The sidebar renders `style` attributes with its CSS variables, which a nonce cannot cover. Styles cannot run code.
- **`connect-src` adds Supabase** (HTTP and WebSocket), because the browser calls Auth directly (PLA-17).
- **One CSP.** `next.config.ts` holds the headers that are the same on every route (HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`); the CSP, with `frame-ancestors 'none'`, comes only from the proxy. The proxy skips `_next/static`, `_next/image`, `/api/inngest` and paths ending in an image, `.txt`, `.xml` or `.webmanifest` extension; those get no CSP but are covered by `X-Frame-Options`. A future route that serves HTML must not end in one of those extensions.

## 2026-10-07 · Migration gates and deploy to `plant-staging` (PLA-11)

- **The reference app's behavior, not its file layout.** Same checks, same `.squawk.toml`, same self-test and the same push-only `db push`, with three differences: (a) the checks on new migrations live in `scripts/check-migrations.sh`, called from the `database` job, because a workflow with `paths:` cannot be a required check; (b) squawk is pinned in `package.json` like the Supabase CLI (PLA-7), with no separate version files; (c) `deploy-migrations` lives in `ci.yml` with `needs: [database]`, because `needs:` only works within one workflow, and the reference's deploy runs in parallel with CI and can apply a migration CI rejects.
- **`needs: [database]`, not `ci`.** A new `pnpm audit` advisory or an unrelated test does not hold back migrations, and the Vercel deploy does not wait for CI either.
- **The append-only check runs only on PRs.** It protects review, not the database: `db push` fails closed when an applied version is deleted or given a new version, and ignores edits. On push it would block the only way out for a migration that never applied (procedure 1).
- **One secret, no personal token.** `SUPABASE_DB_URL` (Session pooler, port 5432) in the `supabase-staging` environment, restricted to the `staging` branch and passed only to the push step. No `supabase link`. Only the push job in `ci.yml` names that environment: the branch rule does not stop other events that run on `staging`, such as `schedule` or `pull_request_target`. Nor does it stop a same-repo PR whose head branch is `staging`, which runs the workflow of the branch it targets, so the environment also requires Tomas's approval: no workflow gets the secret until he approves its run. `deploy-migrations` runs only while `supabase/migrations/` differs from the last `staging` push whose deploy succeeded (read from the Actions API), so only those pushes ask for approval. Tomas approves only a `push` run on `staging`; an approval request from a `pull_request` run is rejected.
- **TLS without certificate verification.** The pooler URI the dashboard gives has no `sslmode`, and the CLI then encrypts without verifying the server certificate. Accepted for now: exploiting it needs a network position between the GitHub runner and Supabase. `sslmode=verify-full` with Supabase's CA is the fix if that changes.
- **`forbidden-words` comes only from `forbidden-words.yml`,** which runs on pushes to this repo. A PR from a fork, or whose head was pushed with `[skip ci]`, never gets that required check and needs a ruleset bypass.
- **Shared database until the beta.** `plant-staging` is also production's database, so migrations are additive only: a `DROP` or `RENAME` waits until production runs code that no longer uses it.
- **Procedures:**
  1. A merged migration that never applied (it failed on the real database or landed out of order). If it failed on `lock_timeout`, first "Re-run jobs". Otherwise a PR moves it with `git mv` to a new timestamp and fixes it there; it is never edited in place, because the push only checks added files. The append-only check stops that PR, so Tomas adds himself as a ruleset bypass actor in "For pull requests only" mode, merges only that PR and removes himself right away. The push checks the new file's name, order and squawk, and the deploy applies it. A failed `CREATE INDEX CONCURRENTLY` leaves an INVALID index behind: the fix PR first adds a migration with only `DROP INDEX CONCURRENTLY IF EXISTS <name>` and the exemption line of `pass-concurrent-index-alone.sql`, then the build under a new timestamp.
  2. With `deploy-migrations` or `database` red on `staging`, the next merge is the fix and nothing else: the next push only checks its own changes. A migration left unapplied goes out with the next push, whatever it changes.
  3. The concurrency group keeps one pending deploy, including one waiting for approval, and the last one queued replaces it, so with merges close together an older SHA can replace a newer one. Nothing is lost: any later push deploys whatever is still unapplied, or "Re-run jobs" on the newest cancelled deploy.
  4. A merge with `[skip ci]` does not deploy until the next push.

## 2026-10-07 · Profiles, consents and audit log (PLA-16)

- **`REVOKE ALL` before every grant.** With `auto_expose_new_tables = false`, a new table in `public` still gives TRUNCATE, REFERENCES, TRIGGER and MAINTAIN to `anon`, `authenticated` and `service_role` by default. Every table runs `REVOKE ALL` from the API roles and removes those four from `service_role`, which with auto-expose off gets nothing else: it ends up with no privileges, and the first server code that uses it brings its own `GRANT`. `schema_rls_and_grants_test.sql` fails if `anon` has any privilege on a table in `public` or `private`, or if anyone other than the owner has one of those four.
- **Extensions:** `CREATE EXTENSION … WITH SCHEMA extensions`, always. In `public` every function of the extension would be exposed as an RPC; the floor checks it. Nothing else goes in `extensions`: the floor fails on a table, function, type, operator, collation or default privilege there that is not an extension's member or the platform's (owned by `supabase_admin`), and on any rule or trigger there, since the floor's other asserts stop at `public` and `private`.
- **Shape of owned tables**: `user_id uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users (id) ON DELETE CASCADE` (the default is what allows inserting without a grant on `user_id`), primary key `uuid DEFAULT gen_random_uuid()` (a sequence id reveals how much others write), every `*_id` reference to another owned table as a composite FK with `user_id` (to a partitioned table, also with its partition key; if the reference is optional, `ON DELETE SET NULL (<column>)` so `user_id` is not nulled) and unique keys that include `user_id` or only columns the server generates (such as `id`). A one-row-per-user table (such as `profiles`) uses `user_id` as its primary key and has no `id`. A uuid that references nothing does not end in `_id` (for example `idempotency_key`), and a list of references goes in a join table, not in a `uuid[]`. `authenticated` writes only through column-level grants, never on `id`, `user_id` or columns the server maintains. A Storage path the user writes carries `CHECK (starts_with(<column>, user_id::text || '/'))`; the floor adds that check with the first table that has one. A partitioned table has primary key `(user_id, <partition key>, id)`, and every partition gets `ENABLE ROW LEVEL SECURITY` and the same `REVOKE ALL` with no grants: it is read and written through the parent. Our own helper functions (not `auth.uid()`) do not go in a `CHECK`, a default, a policy, an expression index or a generated column: they run as the user and would need EXECUTE. Use the expression or a `DOMAIN`, or a column the server maintains with a trigger (for example, the name without accents for search) and a plain index on it. The pgTAP floor checks `user_id` NOT NULL and cascading from `auth.users`, ids without sequences, unique keys with `user_id` or server-generated, that every uuid `*_id` column is its single-column primary key or an FK (paired with `user_id` when it points to another owned table), that there are no `uuid[]` columns, and write grants only per column and never on `user_id`; each table's two-user test covers the rest.
- **Global reference tables** (`fx_rates`, `prices`, `instruments`) arrive with their feature and add a narrow exception to the floor: no `user_id`, only SELECT for `authenticated` and a `FOR SELECT USING (true)` policy. `instruments` has no `service_role` grant either: its migration seeds it.
- **Closed values as Postgres enums** (`reference_dollar`, `consent_kind`), so the generated types bring the unions and the TypeScript does not copy the literals.
- **`consents` is a history.** Withdrawing a consent is a new row with `granted = false`; the current state is the latest row per kind. `granted` has no default, so every row says explicitly whether it grants or withdraws.
- **`audit_log` lives in `private` and has no FK to `auth.users`**, so the trail survives account deletion. It has no policies or grants. PLA-21 decided, on the still-empty table, `outcome` and the action vocabulary (enums) and the shape of `metadata`; the cap and retention come later. `metadata` never carries emails, IPs, amounts or document text.
- **plpgsql_check runs inside pgTAP**, because `supabase db lint` skips trigger functions, which today are all of them.
- **The CI `database` job uses the CLI pinned in `package.json`** (`pnpm exec supabase`) and does not log in to ghcr.io, so the workflow stays at `contents: read`. If the image registry starts rate-limiting pulls, the login gets added.
