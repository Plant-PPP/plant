# Threat model: uploads

> **Superseded by [2026-10-14-uploads-and-reading.md](2026-10-14-uploads-and-reading.md).** The quota it waits on (PLA-42) and the job (PLA-35) are built, and files are deleted 30 days after upload (PLA-43).

Branch `feat/pla-34-signed-upload` (PLA-34). The PR template requires it for a new user-controlled upload and a change in RLS: the files are broker statements, screenshots and spreadsheets with a user's holdings, and the bucket gets the first Storage policies.

## Scope and assets

- **What it protects:** each user's uploaded files in the private `imports` bucket, and their rows in `uploaded_documents` and `imports`: file name, type, size, hash and the import's status.
- **Left out:** reading a file (the job arrives with PLA-35), deleting files after 30 days (PLA-43) and the monthly quota (PLA-42), which Cargar only shows for now.

## Trust boundary

- **The browser** asks for a signed URL, puts the file there itself, and tells the server it finished. Everything it sends is untrusted: the file's name, size and type, the bytes, the account, the upload id and the path. A user can also call PostgREST and Storage directly with their own token.

## Data flow

1. `startUpload` (`lib/imports/write.ts`) checks the name's extension against the allowlist, the declared size, that the terms in force were accepted and that the account is one of the user's open ones. It mints an upload id and the path, `{user_id}/imports/{upload_id}/{object_id}`, and asks Storage for a signed upload URL with the session's token.
2. The browser uploads the file to that URL. The bucket refuses anything over 20 MiB or with a content type outside its list.
3. `finishUpload` checks the path is the user's and the upload's, downloads the file with the session's token, checks its size and its first bytes against the type its name says, hashes it, and files `uploaded_documents` and a queued `imports` row. A file refused here, or one the account already has, is removed.

## Where it is enforced

- **Storage policies:** a user adds, reads and removes objects of the `imports` bucket only under their own folder and its `imports` subfolder; no policy allows an update, so a file is never overwritten after its hash is taken. The MFA gate is a RESTRICTIVE policy on `storage.objects`.
- **Bucket:** private, 20 MiB, the content types Cargar takes.
- **RLS and grants:** the owner predicate and the MFA gate on both tables. `authenticated` writes only a document's file columns and an import's document; never `user_id`, an import's status or a file's deletion date. It may delete its own documents, which deletes their imports.
- **CHECKs:** the path sits under the owner's folder, the type is on the list, the size is at most 20 MiB, the hash is 64 hex characters, the name has no control character or slash; one file per account by hash.
- **Server checks:** the name's extension, the first bytes (`bytesMatch`), the size read back from Storage, and the path against the session's user.

## STRIDE

|       | Vector                                            | Control                                                                                                                                         |
| ----- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** | A request acts as another user                    | The JWT's `sub` is `auth.uid()`; the Storage policies and RLS filter by it, and `user_id` defaults to it with no write grant.                   |
| **T** | A file in another user's folder, or swapped later | The insert policy checks the folder; no update policy exists; the path CHECK ties a document to its owner's folder. pgTAP covers each.          |
| **T** | A file renamed to look like a PDF                 | The server checks the first bytes against the type the name says and removes a file that fails.                                                 |
| **R** | A user denies an upload                           | The document and import rows carry the time; `imports.upload` logs each step with the user's id.                                                |
| **I** | Reading another user's files or rows              | RLS and the select policy return nothing; the bucket is private. Logs carry ids, the type and the outcome, never the file name or its contents. |
| **D** | Huge or many files                                | The bucket and the CHECK cap a file at 20 MiB, and the server reads it only once it is under that. The monthly quota arrives with PLA-42.       |
| **E** | Setting an import to ready, or a deletion date    | No grant on `status` or `delete_after`; the job writes them as `service_role` with PLA-35. The pgTAP ACL test pins every grant.                 |

## Controls as built

- **Owner isolation, the grants and the bucket:** `supabase/tests/uploads_isolation_test.sql`, the Storage assert in `schema_rls_and_grants_test.sql` and `security-tests/src/uploaded-documents.pentest.test.ts` and `imports.pentest.test.ts`.
- **The type and path checks:** `lib/imports/upload.test.ts` and `lib/imports/write.test.ts`.
- **Logs without file names:** `lib/imports/write.test.ts`.

## Residual risk

- **The server reads a file of up to 20 MiB into memory** to check and hash it. One server action at a time per upload keeps it bounded; a quota arrives with PLA-42.
- **A user can file a document row straight through the API** with a hash, size or type that does not match their file. Only their own import suffers, and the job reads the file itself.
