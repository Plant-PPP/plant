# Threat model: login with an email code and Google

Branch `feat/pla-17-login-oj22lx` (PLA-17). Required by the PR template because the change adds authentication, a route handler, a redirect and a migration on `auth.users`.

## Scope and assets

The session (access and refresh tokens in cookies), the right to sign in as an address, and every page behind `(app)`. Out of scope: MFA (PLA-18, PLA-76); audit rows and telemetry are in `2026-10-08-logs-audit.md` (PLA-21).

## Trust boundary

The email address, the code, `next`, the `error` query parameter, the callback's `code`, `error` and `error_code` parameters, the `plant-auth-next` cookie and every request header come from the browser. Google's identity comes through Supabase Auth, which verifies it.

## Data flow

1. `/login` (Server Component) reads Auth's settings to decide whether to show Google.
2. The browser calls Auth directly: `signInWithOtp`, then `verifyOtp`; or `signInWithOAuth`, which returns through Google to `/auth/callback` with a PKCE code.
3. `/auth/callback` exchanges the code with the verifier cookie and redirects to the sanitized `next` cookie.
4. On every page request `proxy.ts` verifies the access token (`getClaims`, local ES256 verify) and refreshes it when it has expired or has under 2 minutes left, so a Server Component never refreshes and drops the rotated cookies. With the legacy HS256 secret, `getClaims` asks Auth instead, so the hosted project must use asymmetric signing keys (staging checklist).
5. `(app)/layout.tsx` calls `getSessionClaims()` and renders the user from the `email` claim.

## Where it is enforced

- **Postgres:** the `clear_password` trigger on `auth.users`.
- **Supabase Auth config:** confirmations, code length and expiry, resend interval, exact redirect URLs, session limits.
- **`proxy.ts`:** refresh, the redirect to `/login`, stripping a client's `x-plant-auth`.
- **`/auth/callback`:** PKCE exchange, `sanitizeNextPath`, `no-store`.
- **`lib/auth/`:** `sanitizeNextPath`, `nextAuthCode`, the closed error-copy map, `isSessionMissing`, `getSessionClaims`.

## Residual risk

- **Hosted Auth is not tested continuously.** The specs run against the CLI's Auth; the staging checklist covers the dashboard settings.
- **An XSS that gets past the CSP steals the session**: the cookies are readable by JavaScript. The CSP has no violation reports until client error reporting (PLA-88).
- **Shared server IP** for the callback exchange and refreshes, until IP forwarding (before the beta).
- **Up to 1 h of access** after sign-out, deletion or a ban. When Auth cannot revoke at sign-out (an outage, a rate limit), this device is still signed out but the session lives until its limits end it, so a token copied earlier keeps working.
- **Rows written with triggers off keep their password** (a data-only restore or a bulk import sets `session_replication_role = replica`) until the row's next write; one password sign-in on such a row still succeeds before its own write clears the hash. After a data-only restore or bulk import, re-run the migration's blanking `UPDATE`.
- **A stolen session can still act as the user** while it lives: `PUT /user` with a password returns 200 and signs out the user's other sessions even though nothing is stored, and an email change or a new sign-in method would outlast sign-out if the dashboard allowed it. "Secure email change" on and every other sign-in method off (staging checklist) keep a stolen session from adding a credential.
- **Code guessing is limited per IP only** (30 verifies per 5 minutes): an attacker with many IPs gets about 60 guesses per IP for each 10-minute code, with no captcha (recorded decision). Accepted while only the team signs in; revisit before the beta.
- **A relayed code is a takeover:** anyone who gets the user to read out a code signs in as them. The mail says not to share it and that Plant never asks for it.
- **A refresh racing a sign-out** (a prefetch rotates the token while "Cerrar sesión" revokes the session) can land fresh cookies after the browser cleared them; the access token then verifies locally until it expires, up to 1 h.
