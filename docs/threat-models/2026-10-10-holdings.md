# Threat model: holdings and instruments

Branch `feat/pla-25-holdings-valuation` (PLA-25). Required by the triggers "New field with financial or personal data" and "Change in authentication, session, MFA or RLS": it adds `holdings`, the user's amounts and positions, as an owned table with RLS, and `instruments` as a third global reference table. It extends [the holders and accounts model](2026-10-09-holders-accounts.md), whose lock, stamp and guards it reuses.

## Scope and assets

- `public.holdings`: what each user holds in each account and portfolio: units of an instrument, a cash balance, a fixed term's principal and rate, or a stated value with its date and label.
- `public.instruments`: the symbols a holding can name (BTC, ETH, SOL, USDT, USDC). Market data, the same for every user.
- The invariants that an active holding sits in an active account and portfolio of its own user, and that an account's portfolio holds one active position per instrument.
- `@plant/core` valuation: pure functions that value holdings the caller passes; they read no database and log nothing.

Out of scope: the holdings reader, the screen and its writes (PLA-28), and the daily valuation job (PLA-27).

## Trust boundary

The browser talks to PostgREST with the user's JWT (role `authenticated`) or without a session (`anon`). Everything the client sends is untrusted: ids, `source_connection_id`, `portfolio_id`, `instrument_symbol`, amounts, rates, dates, labels, `archived_at`, filters, embeds, `Prefer` headers and `on_conflict`. No app code writes holdings yet; any client can with its own token.

## Data flow

1. A client inserts or updates a holding through PostgREST with its JWT.
2. The `portfolio_setup_*` triggers take the user's advisory lock (on insert and on an update that sets `portfolio_id` or `archived_at`), default the portfolio to the account's, stamp `archived_at` and run the holding guard. The portfolio and account guards now also check for active holdings.
3. Later (PLA-27/28) a server reads holdings and a quote snapshot and calls `valueHoldings`.

## Where it is enforced

- RLS `holdings_owner`: `user_id = (select auth.uid())` in `USING` and `WITH CHECK`, plus the restrictive MFA gate on both tables. `instruments_select_all` lets `authenticated` read every instrument.
- Column grants: `authenticated` inserts the class fields, the account and the portfolio, and updates the portfolio, the amounts, rate, dates, label and `archived_at`. Never `user_id`, `id`, the account, the class or the instrument; no `DELETE`; `anon` and `service_role` hold nothing on either table. Nobody writes `instruments`, `service_role` included: its migration seeds it.
- Composite foreign keys `(user_id, source_connection_id)` and `(user_id, portfolio_id)`: a holding points only at its own user's account and portfolio, and another user's id, active or archived, fails like a random one (`23503`, or `23502` when the portfolio is left to the default), with no hint.
- CHECKs: one branch per class, a positive amount that is not NaN, a rate from 0 to 10, dates from 1900 to 9999, labels of 1 to 80 characters with no outer spaces.
- A partial unique index on `(user_id, source_connection_id, portfolio_id, instrument_symbol)` among active instrument holdings. It leads with `user_id`, so another user's position never collides.
- Guards and the default trigger (`SECURITY INVOKER`, `search_path = ''`, not executable by the API roles), keyed on the row's `user_id`: refused with `PT409` and a hint are archiving an account or portfolio with active holdings, and an active holding in an archived account or portfolio.

## STRIDE

|       | Vector                                                                        | Control                                                                                                         |
| ----- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **S** | Creating a holding in another user's name                                     | No grant on `user_id`; `WITH CHECK` against `auth.uid()`                                                        |
| **T** | Editing, moving, archiving or deleting another user's holding                 | `USING` by `user_id` filters the update to nothing; no `DELETE` grant                                           |
| **T** | Putting a holding in another user's account or portfolio                      | Composite foreign keys to the user's own rows                                                                   |
| **T** | Writing an instrument                                                         | No API role holds a write on `instruments`                                                                      |
| **R** | Not knowing when a holding was archived                                       | `archived_at` is stamped by the database                                                                        |
| **I** | Reading another user's holdings, or probing their ids by a key, hint or embed | RLS by `user_id`, also on embedded tables; foreign keys and the unique index answer the same as for a random id |
| **D** | Archiving an account or portfolio out from under active holdings              | The guards, serialized by the per-user lock                                                                     |
| **D** | A stored value the app cannot read (infinity, a five-digit year, NaN)         | The CHECKs, mirrored by core's schema and pinned by parity tests                                                |
| **E** | A guard or trigger used to read another user's rows                           | They key on the written row's `user_id`, run as the caller, in `private`, not executable by the API roles       |

## Controls as built

- **pgTAP** (`supabase/tests/holdings_isolation_test.sql`): the exact grants, the trigger definitions and order, the functions' settings and execute rights, the foreign keys, the column types, the instruments seed, the lock on insert, move and archive but not on an amount edit, isolation between two users, every CHECK edge, the unique index (an archived position does not block a new one, a restore beside an active one is refused, two accounts may hold the same instrument, another user's position answers `23503`), every guard and its hint, another user's active or archived account and portfolio answering with no hint, the owner moving, archiving and restoring their own holding, the server's columns refused, and the cascade on account deletion. The floor (`schema_rls_and_grants_test.sql`) lists `instruments` as the third reference table, asserts `service_role` holds nothing on it, and pins `service_role` inserting only into the quote tables.
- **PostgREST** (`security-tests/src/{holdings,instruments}.pentest.test.ts`): the shared cross-user cases, a holding into another user's or a random account and portfolio (`23503`/`23502`, no hint), `source_connection_has_holdings` over HTTP, and the shared read-only cases on `instruments`.
- **Core** (`packages/core/src/valuation/*.test.ts`): the schema mirrors the class CHECK and the rate bound, read from the migration.

## Residual risk

- **Planned or estimated counts** (`Prefer: count=planned`) come from table statistics over every user's rows, so they hint at platform-wide totals, never at one user's rows. This holds for every owned table and is accepted.
- **The generated types read `amount` and `annual_rate` as numbers.** PLA-28's reader selects them as text before valuation, so no amount passes through a float.
- The holders and accounts model's residual risks hold here too.
