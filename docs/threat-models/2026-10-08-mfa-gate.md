# Threat model: the MFA rules (access token hook, RESTRICTIVE policies and the app's checks)

Branch `claude/pla-18-mfa-rules-pr4upg` (PLA-18). Required by the PR template because the change touches MFA, sessions, policies and grants. Part 1 covers the hook and the role; the Part 2 section covers the RESTRICTIVE policies, the proxy's MFA check and the sensitive-action rule.

## Scope and assets

Every row a user owns, reached with an access token. The change decides which role an access token carries and adds `mfa_enrolled` to it. Out of scope: the MFA screens and audit rows of factor changes (PLA-76), the "factor enrolled" mail (PLA-75), the RESTRICTIVE policies and the app's checks (part 2).

## Trust boundary

Supabase Auth mints and signs the token and calls the hook with its own role, in its own transaction. The hook reads `auth.mfa_factors`, which only Auth writes. The browser chooses which session to present; PostgREST trusts the token's `role`.

## Data flow

1. A sign-in (email code, mail link, Google), a refresh or a TOTP verify asks Auth for an access token.
2. Auth calls `private.custom_access_token_hook` as `supabase_auth_admin` with the user id and the claims it is about to sign (`aal`, `amr`, `role`).
3. The hook adds `mfa_enrolled` and, for an enrolled user below `aal2`, sets `role` to `authenticated_aal1`.
4. PostgREST switches to the token's role through `authenticator`. `authenticated_aal1` holds no grant, so every table, view and function answers 42501.
5. The session climbs to `aal2` with Auth's challenge and verify, which issue a new token with `role: authenticated`.

## Where it is enforced

- **Postgres:** the hook (`supabase/migrations/20261008202150_mfa_hook.sql`), the role and its missing grants.
- **Supabase Auth:** calling the hook (`config.toml` locally, the dashboard on hosted), and the per-session `aal` check on enrolling, removing a verified factor and changing the email.
- **Auth settings:** the first-factor `amr` methods prove the mailbox only while phone sign-in, SMS codes, other providers, passkeys, SAML, linking, third-party and Web3 tokens are off.

## Controls as built

- **Hook over the truth table:** `supabase/tests/mfa_gate_test.sql` (both claim values, `aal1`, `aal2` and absent; a user with only an unverified factor; a user whose only verified factor is a phone factor; another user's claims set on the request; a non-`authenticated` role left alone).
- **Role and hook grants:** `supabase/tests/schema_rls_and_grants_test.sql`, with canaries.
- **Real tokens:** `security-tests/src/mfa.pentest.test.ts`: a code-only session of a user with TOTP gets 42501 on every `public` table and view, stays demoted when refreshed, cannot enroll, unenroll or change the email, and its token carries a first-factor `amr` and the claim; a second code-only session verifies TOTP, reads its profile and ends the first; removing the factor at `aal2` lifts the demotion on the next refresh; a user without a factor keeps `authenticated`; linking and phone sign-in are refused.
- **Settings:** `apps/web/src/lib/auth/otp-config.test.ts` and `security-tests/src/auth.pentest.test.ts`.

## Residual risk

- **What a demoted token still reaches at Auth:** `GET /user`, `PUT /user` with `data`, reauthentication (which mails the owner a code, within Auth's rate limits), sign-out, and challenge and verify, which need the TOTP code. A global sign-out ends the owner's other sessions too: a thief can sign the owner out everywhere, but reads nothing.
- **A token minted before enrollment keeps `mfa_enrolled: false` and its role until it expires** (the JWT expiry, 1 h by default).
- **A planted factor evicts the owner**: every TOTP verify deletes the user's other `aal1` sessions. Countermeasures: every hosted MFA factor off until PLA-76, the enrollment mail after PLA-75, PLA-76's global sign-out on the verify screen, and support's runbook (prove the mailbox, `auth.admin.mfa.deleteFactor`, global sign-out). Removing a factor ends no session: a stolen code-only session gets its full access back at its next refresh, so a factor removal always comes with a global sign-out.
- **Hosted settings drift**: the dashboard is the source of truth on hosted, and the tests see only `config.toml` and the CLI's Auth. The PR checklist runs `GET /auth/v1/settings` against staging.
- **The frozen `production` branch runs code from before this change against the same project.** Part 1 changes nothing for users without a factor, and no hosted user has one.

## Part 2: the RESTRICTIVE policies and the app's checks

### Scope and assets

Every row in `public`, reached with a token the hook did not demote: one minted while the hook was off, or one whose claim says the user has no factor. And the three sensitive actions (export, account deletion, email change), which arrive with PLA-58, PLA-84 and the account screens and call `requireSensitiveSession`. Out of scope: the `/auth/mfa` screen and audit rows of MFA changes (PLA-76), the `sign_in_again` flow and audit rows of denied actions (PLA-58, PLA-84).

### Data flow

1. The proxy verifies the token (`getClaims`) and reads `aal` and `mfa_enrolled` with `mfaRequirement`. On a private path, a session that needs the code is sent to `/auth/mfa?next=…`; a token without the claim gets the retry page, and `x-plant-auth: mfa_claim_missing` on the forwarded request.
2. Server code calls `getSessionClaims()`, which throws on that header and repeats the check on its own `getClaims`.
3. PostgREST runs every query against `public` through the owner policy and the RESTRICTIVE one; both must pass.
4. A sensitive action calls `requireSensitiveSession`, which reads `amr` from the verified claims.

### Where it is enforced

- **Postgres:** the RESTRICTIVE policy (`supabase/migrations/20261009061334_mfa_gate.sql`) on every `public` table; the floor in `schema_rls_and_grants_test.sql` fails on a table without it.
- **App:** `proxy.ts` (redirect and claim check), `getSessionClaims()` (the same for server code), `requireSensitiveSession` (first-factor sign-in in the last 15 minutes).

### Controls as built

- **Policy over the truth table:** `supabase/tests/mfa_gate_test.sql`, with the claims a real token carries; `profiles_consents_isolation_test.sql`, `audit_log_test.sql` and `ai_costs_isolation_test.sql` set them too.
- **Floor:** `schema_rls_and_grants_test.sql` (one RESTRICTIVE policy per `public` table, name, role, command and expression; no partition granted to `authenticated`). The policy assert was seen failing before the migration, and canaries prove both asserts can fail.
- **App rule parity:** `apps/web/src/lib/auth/mfa-rules.test.ts`.
- **Proxy and server code:** `proxy.test.ts`, `session-claims.test.ts`, `sensitive-session.test.ts`, `instrumentation.test.ts`.

### Residual risk

- **`/auth/mfa` answers 404 until PLA-76.** No hosted user can be enrolled before then, since every factor stays off.
- **A 15-minute-old sign-in is a window, not a proof of presence:** a thief who steals a session right after the owner signs in has the rest of it.
- **The sensitive check runs only where it is called.** PLA-58, PLA-84 and the email change screen must call it; nothing fails if they don't, beyond their own tests.
- **The policy's expression is copied into every new table's migration.** The floor catches a missing or altered copy, not a table outside `public`; those rely on part 1's role.
